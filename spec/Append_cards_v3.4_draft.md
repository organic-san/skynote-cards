## 1. 圖片上傳【待確認】

> v3 草案 2 §8 把「圖片與檔案的保存（例如課表圖片、檔案傳輸）」列為暫不處理。2026-11-08 的討論把它排到 v3.4。

### 1.1 現況：顯示已經有，缺的是放在哪

- 內文寫 `![](https://…)` 就會顯示成圖片（`render.ts` 的 markdown-it 預設就渲染圖片；`html: false` 只跳脫原始 HTML）。
- 網址欄填圖片網址，卡片頁會嵌入（`embed.ts`，認 `.png` `.jpg` `.gif` `.webp` `.avif` `.svg`）。

所以缺的是**一個放圖片的地方**。外面的選項都不理想：

- 公開的圖床（例如 Imgur）不適合私人內容。
- Google Drive、Google 相簿的分享連結不是直接的圖片網址，`embed.ts` 認不出來，`![]()` 也顯示不了。
- Discord 的附件網址會過期，直接貼過來，過一陣子就打不開。

### 1.2 用途【待確認】

用途決定備份策略（§1.4），要先問清楚：

- **資訊的截圖與照片**（課表、看到的情報）：量多，多半用過就不再看，畫質不重要。
- **自己的作品**（繪圖環境的進度）：要長期保存，在意畫質，需要備份。

### 1.3 做法：存進自己的 bucket

- **上傳**：瀏覽器端先縮圖再送（canvas 轉 webp，長邊約 1600px，幾百 KB）。手機照片不會太大，也碰不到 App Engine 單一請求 32MB 的上限。
- **入口**：Markdown 工具列多一顆，或在文字框裡直接貼上截圖。插進文字框的是一行 `![](/img/<雜湊>.webp)`，跟工具列其他按鈕一樣只是插語法（v3.2 §4）。
- **存放**：bucket 裡的 `images/<內容雜湊>.webp`，跟 `cards/` 分開。用內容雜湊當名字，同一張圖上傳兩次只存一份。
- **讀取**：`GET /img/<雜湊>.webp` 由伺服器讀 bucket 回傳。bucket 是私有的，IAP 擋在前面。
- **本機與 VM**（沒有 bucket）：存在語料庫的 `images/`。

### 1.4 代價

- **快取**：IAP 會把每個回應的快取標頭改成 `no-cache, must-revalidate`（v3.1 §4.3 踩過）。圖片是延後載入，不會造成 Ferdium 換頁時的閃爍，但每看一次都要回伺服器問一次。用內容雜湊當 `ETag`，重看時只回 304，不必重傳。
- **備份要選一邊**：
  - 進 Git：語料庫 repo 會越來越胖，每次 clone 都拖著。
  - 不進 Git：只有 bucket 一份，可以開 bucket 的物件版本保留當保險。
  - 本機與 VM 的 `images/` 在語料庫裡，自然進 Git，所以兩種部署的行為會不一樣。
- **對帳與「更新」**：開機對帳（`reconcile.ts`）與側欄的「更新」（v3 §7）目前只處理 `cards/`，要明確決定 `images/` 納不納入。
- **站外**：下載的 `.md` 與複製出去的內文（v3 §6.1、v3.3 §1）裡，`/img/…` 是站內路徑，拿到站外圖片不會跟著。
- **刪卡**：反芻期內刪掉的卡留下的圖片沒有人指著。以個人用量來說可以不清。
- **工作量**：上傳端點、圖片路由、縮圖的前端、工具列的按鈕、測試，差不多是一個小版本。

### 1.5 跟其他項目的關係

沒有標題的資料（v3.3 §6）收的零碎外部內容，常常就是一張截圖。這一項做了之後，那裡可以直接帶圖。

## 2. 未被引用的卡片可以一直修改【暫緩】

> v3 決定反芻期暫時保留（v3 草案 2 §9），v3.1、v3.2、v3.3 沒有處理。本節保留提案與分析，等需要時再決定。

### 2.1 動機

反芻期（R5，預設 8 小時）原本的用意，是留一段時間回頭審視與潤飾（v2 D.1）。實際用下來，這個期限對修正小錯誤與補述的意義不大。

檢查它實際保護了什麼：需要保護的是**被依賴的東西**，而那由 R6 負責——被指向的卡片定案（v2 D.2）。沒有被指向的卡片，改了也不會讓任何結構化連結失效（正文裡的段落連結見 §2.5）。時間限制在 R6 之外多擋下的，是對沒人依賴的卡片所做的修改，小修正與補述就屬於這一類。

v3 的產出已經走在前面：產出不設反芻期，被引用之前修改、加連結、刪除都不受時間限制（v3 §3）。本節要決定其他型別是否跟進，以及跟到哪裡。

### 2.2 做法一：只放開文字欄位（本草案建議）

**R5（修訂候選）. 卡片自建立起有一段反芻期，長度由 `EDIT_WINDOW_HOURS` 決定，預設 8 小時。反芻期只管連結的新增（R7）與刪除（R9）；文字欄位的修改不受反芻期限制，只受 R6 限制。**

v2 D.3 的修改約束改為：

| | 反芻期內、未被引用 | 反芻期後、未被引用 | 被引用（R6） |
|---|---|---|---|
| `title` `body` `tags` `url` `provenance` `source_*` | 可改 | 可改 | 不可改 |
| `links` | 只增不減（R7） | 不可新增 | 不可新增 |
| 刪除整張卡（R9） | 可以 | 不可以 | 不可以 |
| `type` `id` `created` | 不可改 | 不可改 | 不可改 |

連結與刪除留在反芻期內，理由有三：

- **刪除是連結的配套。** R9 存在是因為 R7：連結選錯收不回，只能整張刪掉重建（v2 D.4）。如果連結可以一直加、刪除卻只限反芻期，反芻期後加錯的連結就再也沒有補救的方法。兩者必須同一個期限。
- **反芻期後的關聯是新的思考。** 「發現兩個舊想法有關，本身就是一個新的思考，它應該有自己的節點」（MVP I4）。反芻期後要把舊卡連到更舊的卡，就發一張新卡同時指向兩者。
- **刪除比修改重。** 修改留下同一張卡，刪除讓它從時間軸上消失。手滑通常當下就會發現，反芻期足夠。

R4 的但書「反芻期內的修改視同建立的一部分」改為「修改視同建立的一部分」：不論何時修改，都要通過當下的現行規則。規則收緊之後，修改一張不合新規則的舊卡，要在同一次修改裡讓它合規（例如沒有標籤的舊 `thinking`，v3 §4）。

### 2.3 做法二：全部不設期限，比照產出

連結的新增與刪除也取消期限，「能不能動」只剩「有沒有被引用」一個判準。

- **好處**：規則只有一條，反芻期整個退場，所有型別與產出一致。
- **代價**：反芻期後加錯的連結只能整張刪掉重建，而重建會換掉 ID 與建立時間，對一張舊卡來說就是失去它在時間軸上的位置。
- **產出接受這個代價的理由**，是改稿時補上取材的連結是常態（v3 §3）。其他型別沒有這個需要。

### 2.4 連帶的變化

- **判準拆成兩個**（做法一）：「文字能不能改」只看 R6；「連結與刪除能不能動」看 R5 與 R6。
- **卡片頁**：meta 行末尾的「尚可編輯 N 小時」（v2 D.5）移除。文字能不能改不再有期限，留著這個倒數，會讓人以為時間到了就不能改。「編輯」鈕照舊只在可改時出現，判準改為「沒有被引用」。
- **編輯頁**：做法一的倒數改說連結與刪除的期限，例如「連結與刪除還剩 3 小時」；反芻期後，新增連結的區塊與刪除鈕不再出現，換成一行說明。做法二沒有倒數，比照產出。
- **鎖定時的訊息**：只剩被引用一種原因。
- **R14**：未被引用的卡片本來就能改，R14 實際作用的只剩被引用的卡片，以及不更新 `revised`（v3 §2）。
- **`revised`**：每次修改照舊更新。卡片頁的「改於」會比以前常出現，這是預期的。
- **沉澱清單**：已在 v3.1 移除（v3.1 §3），不受影響。
- **已被取代的卡（v3.2 §2）**：被 `updates` 或 `refutes` 指到就是被引用，R6 照舊鎖住，不受本節影響。

### 2.5 風險：手動貼上的段落連結

R6 只看 frontmatter 的 `links`（v2 G 節「否決正文引用參與定案鎖定」維持，見 v3 草案 2 §9）。應用程式產生的段落連結只有一個來源：來源面板的「引用」鈕，而那條路徑一定帶著指回同一張卡、拿不掉的連結（v2 C.3、R7），所以都在 R6 的保護範圍內。

不受保護的只剩手動貼進正文的網址。期限放開之後，它們指向的段落可能位移；需要穩定的錨點時，建立連結。

## 3. 環境的刪除與卡片的移動【暫緩】

v3.1 提供了環境的建立與改名（v3.1 §2.7）。刪除與移動還沒有介面；需要時的做法如下。

### 3.1 卡片在環境之間的移動

**現況**：在別處的 clone `git mv` 到另一個資料夾、push，再按側欄的「更新」（v3.1 §2.3）。整批搬移（例如把（無環境）搬空）用這條路最省事，也是 v3.1 預期的用法。

**若要在網頁上做**：移動在資料面只是搬動檔案，內容逐位元不變。ID、連結、`/c/{id}`、段落錨點都不受影響，所以不牴觸不可變，也不需要動規則。做法比照環境改名，只是單位是一張卡：

- bucket 先用新名字存一份，成功才刪舊名字；標記的決定方式與改名相同（v3.1 §2.7）。
- 本機搬檔、索引的 `env` 換掉，一個 commit（例如 `mv {id} {舊環境} → {新環境}`）。
- 入口：卡片頁 meta 行旁的一個動作，選目標環境。

**要決定的事**：

- v3.1 §2.6 說「建立之後不能改環境」，那條是為了不讓環境變成一個需要維護的屬性。開放移動就推翻它；放錯了的卡目前只能在反芻期內刪除重建（產出在被引用之前），被引用之後就留在原處。
- 移動要不要受反芻期或定案限制。內容不變，R6 要保護的段落錨點不受影響，所以沒有理由限制；但「定案的卡還在動」可能違反「寫完不必回頭維護」的直覺。

### 3.2 環境的刪除

- **只刪空的環境**：資料夾裡沒有任何卡才可以刪，效果是刪掉那個空資料夾。有卡的環境要先把卡搬走（§3.1）或刪掉（R9，只限反芻期內）。這樣刪除永遠不會帶走卡片。
- 空的環境不在 git 與 bucket 裡（v3.1 §2.7），App Engine 換機器時本來就會消失；需要刪除的情境主要是建錯名字又不想改名、或本機與 VM 上留著的空資料夾。
- 入口：環境面板裡（v3.1 §2.8），只在空的環境那一列出現，例如改名表單旁的一顆「刪除這個環境」。排過序的話，`envs.yml` 裡的名字一起拿掉。

## 4. Markdown 的鍵盤快捷鍵【待確認】

> v3.2 §4.6 列為不做（「這次沒提。要加的話是同一支 `mdbar.js` 裡的幾行」）。2026-11-09 排到 v3.4。

### 4.1 做法

- 文字框裡按下快捷鍵，等於按工具列上那一顆（v3.2 §4.3）：走同一個 `window.skynoteMd.edit`、同一條 `execCommand('insertText')`，所以一樣進復原紀錄，再按一次一樣是拿掉。
- 只接在掛了工具列的文字框上（`data-mdbar`：內文與碎片的大文字框；隨手記沒有）。
- Windows 用 Ctrl，Mac 用 ⌘（`ctrlKey || metaKey`）。輸入法組字中（`isComposing`）不接。
- 接到的鍵 `preventDefault`，不讓瀏覽器或外層的 Ferdium 另外處理。

### 4.2 哪幾個鍵【待確認】

建議只接慣例明確的幾個：

| 鍵 | 動作 | 備註 |
|---|---|---|
| Ctrl+B | 粗體 | 通用慣例 |
| Ctrl+I | 斜體 | 通用慣例 |
| Ctrl+K | 連結 | GitHub、Notion 的慣例。不接的話 Chrome 會把它當成「搜尋」 |
| Ctrl+E | 行內程式碼 | GitHub、Notion 的慣例 |

待辦、清單、編號、引用這幾個是整行的動作，沒有通用的慣例（GitHub 用 Ctrl+Shift+7、8 之類），建議先不接。

### 4.3 改動檔案

| 檔案 | 改動 |
|---|---|
| `public/js/mdbar.js` | 文字框的 `keydown`：對到按鍵就走同一個 `edit` |
| `test/` | 按鍵對到動作（在 vm 裡跑，同 v3.2 §4 的測試） |

真的按下去的焦點、復原與 Ferdium 裡會不會被攔走，要在瀏覽器裡看。

## 5. 來源面板插入引用之後，Ctrl+Z 退得回去【待確認】

> v3.2 §7 列為暫不做。2026-11-09 排到 v3.4。

### 5.1 現況

從卡片頁 `+` 進來的表單，左邊的來源面板有「引用」鈕（v2 C.3），按下去把那一段的引用插進內文。`sourcepane.js` 是直接改 `value` 再自己發一次 `input`，所以插進去之後按 Ctrl+Z 退不回去，跟工具列（v3.2 §4.5）不一致。

### 5.2 做法

換成工具列同一種寫法：先把選取範圍設到插入點，用 `execCommand('insertText')` 插入，改的字進瀏覽器的復原紀錄，`input` 事件也由瀏覽器自己發。這個 API 不能用時才退回直接改 `value`，代價跟工具列一樣：復原紀錄斷在那一步。

插入點、前後補的空行照舊。

### 5.3 改動檔案

| 檔案 | 改動 |
|---|---|
| `public/js/sourcepane.js` | `insertQuote` 改用 `execCommand('insertText')`，不能用時退回改 `value` |

復原只能在瀏覽器裡驗：插入一次引用，按 Ctrl+Z 回到插入前，再按一次 Ctrl+Y 回來。

## 6. 側欄的環境：膠囊與環境色【方向已定，細節待確認】

> v3.3 拿掉側欄的「首頁」又補回來（v3.3 §4），留下這個問題。2026-11-09 討論之後，使用者決定方向是膠囊化與環境色，排到 v3.4。

### 6.1 問題

側欄上同一種底色同時說兩件事：

- **你在哪一頁**：首頁、搜尋、標籤。
- **你在哪個環境**：環境清單裡所在的那一列，在這個環境的每一頁都亮著。

所以在首頁時「首頁」與所在環境那一列同時亮著，到了卡片頁又只剩環境那一列，規則看起來不一致。環境與頁面是兩種不同的「選中」，應該用兩種不同的東西表示。

### 6.2 使用者的條件

| | 條件 | 理由 |
|---|---|---|
| a | 一下就能切換環境，環境清單一直攤開 | 切換得很頻繁，兩層選單（先點開、再選）不方便 |
| b | 不佔空間、用文字 | 圖示欄太佔空間，名字的頭一個字也表達不夠 |
| c | 明確、簡潔地知道自己在哪個環境 | 內容區上方的麵包屑不夠明顯 |
| d | 有固定位置的首頁 | 不必每次先判斷哪一列才是首頁（v3.3 §4.2） |

### 6.3 討論過、沒有採用的做法

| 做法 | 例子 | 不採用的原因 |
|---|---|---|
| 側欄頂端放目前的環境名稱，點開下拉切換 | Notion、Linear、Slack | 違反 a |
| 最左邊一條環境圖示欄 | Discord、Arc | 違反 b |
| 內容區上方的麵包屑（「故事 › 卡片」） | GitHub、Google Drive | 違反 c；側欄同時亮兩列的問題也還在 |
| 環境本身就是頁面，不另設首頁 | Todoist | 違反 d（就是 v3.3 拿掉「首頁」時的樣子） |
| 底色只標頁面，所在環境改用細線或粗體 | — | 整合度不夠 |
| 頂端大標題寫目前的環境，點它回首頁，下面是環境清單 | — | 整合度與方便性不夠 |
| 樹狀展開：所在的環境展開，底下才有首頁、搜尋、標籤 | Linear 的團隊、Notion 的 Teamspaces | 首頁跟著環境的位置跑，違反 d |
| 環境排成頁籤 | 試算表的工作表頁籤 | 六個環境的名字排不下，手機更不行 |

### 6.4 方向：膠囊加上環境色

```
Skynote
(故事) (繪圖) (學校)        ← 環境：膠囊，點一下切換；目前的那顆用它的顏色填滿
(專題) (自我省思)
─────────
█ 首頁                     ← 只有頁面用灰色底色
  搜尋
  標籤
─────────
＋ 追加外部資料
  更新
```

- **膠囊**：環境本來就是一種範圍篩選（它決定時間軸、標籤、搜尋看到什麼），跟時間軸的型別篩選列用同一套樣子。膠囊與清單的列是兩種元件，不會跟頁面的選取混在一起。排不下就自動換行。
- **環境色**：每個環境一個顏色。顏色告訴你在哪個環境，灰色底色告訴你在哪一頁。
- **「首頁」**在膠囊區下面的固定位置。環境的數量不常變，膠囊區的高度也就不常變。
- 環境面板（齒輪）照舊負責新增、排序、改名；膠囊的順序跟面板裡排的一樣。

### 6.5 要決定的事

- **環境色的強度**：
  - 輕：只有目前那顆膠囊用它的顏色填滿。
  - 中：整個側欄的底色帶一點目前環境的顏色。
  - 重：整頁的背景都帶一點環境色。手機上側欄收起來時也看得出在哪個環境。
- **顏色怎麼來**：使用者在環境面板裡挑（要存進 `envs.yml`，它目前只是一份名字的清單），或由系統依順序或名字自動分配。
- **跟型別色的關係**：卡片的五種型別已經用了鮮明的顏色（色點，v3.1 要求彼此在 OKLab 上拉開距離）。環境色只能是很淡的底色，不能再是鮮明的點或線；要確認在 Ferdium 裡看起來也舒服。
- **手機**：側欄收起來時看不到膠囊。要不要在選單鈕旁邊放一顆目前環境的膠囊（點了回首頁），或靠「重」的整頁底色。
- （補強，可選）快捷鍵直接切換第 n 個環境。
