## 1. 版本定位

v2 的設計假設是「單一主題、長脈絡的深入思考」；實際用法是「把想法連起來，做短脈絡的延伸」（草案 2 §1）。v3 依循一條原則：**機制只提供原件，流程留在使用習慣裡。**

本版做的事：

1. **補一個原件：勾選**（§2）。
2. **把產出從思考分出來**（§3）。產出不設反芻期，被引用之前都可以改稿。
3. **隨手記只寫碎片**（§4）。R11 因此不必在隨手記另外處理。
4. **側欄加「更新」**（§7）。手動調整語料庫之後，結果拉得回來。
5. **側欄下半依頁面切換，加上三項介面調整**（§5、§6）。

## 2. 待辦勾選

### 2.1 語法

`[ ]`（未完成）與 `[x]`（完成，`[X]` 同義）渲染成可以點的核取方塊。標記必須在清單項目的開頭：

```markdown
10/7
- [ ] 09:00 交作業
- [x] 買車票
1. [ ] 也可以用編號清單
```

行首沒有清單記號的 `[ ] 事情` 不是標記。這與 GitHub 及其他 Markdown 工具的寫法一致，下載的 `.md`（§6.1）拿到別處仍然是待辦清單。

### 2.2 規則

**R14. 切換勾選標記不算修改卡片，不受反芻期（R5）與定案（R6）限制。**

- **不算修改**：不可變的意義在於寫完不必回頭維護，不在於禁止狀態改變。勾選記錄的是「這件事做完了」，不是內容的修訂。
- **不牴觸 R6**：R6 守護段落錨點 `#b{n}`。切換一個字元不改變區塊的數量與順序，錨點照舊有效。

邊界：

1. 一次請求只改一個標記，只在 `[ ]` 與 `[x]` 之間互換。**內容只差那一個字元。** 檔案照一般的寫入路徑重新產生，frontmatter 的寫法可能因此變得與手改的版本不同。
2. 新增或刪除項目、修改項目的文字，是編輯，受反芻期限制（產出除外，R15）。
3. 勾選不更新 `revised`。變更留在 git 歷史裡。
4. 勾選不改變反芻狀態，不影響沉澱清單。

### 2.3 實作

- **渲染**：`render.ts` 加一條 markdown-it 規則，做法比照 `block_anchor`：清單項目開頭的標記換成核取方塊，依出現順序給 `data-task="k"`（從 0 起）。
- **定位**：路由以 `render.ts` 的解析結果（token 的來源行號）找出原文裡第 k 個標記，不另寫正規表示式。程式碼區塊裡的 `- [ ]` 不是標記，兩套判斷遲早會對不上。
- **分層**：定位在路由完成，因為 service 不能引用 web 的 `render.ts`（v2 F 節的單向依賴）。service 只收到那個位置，換掉那一個字元。
- **端點**：`POST /c/:id/tasks/:k`，內容為 `{ "checked": true, "rev": "…" }`。`rev` 是頁面載入時卡片內容（標題、標籤、網址、內文）的雜湊；與現況不符回 409，前端重新載入。勾選成功時回傳新的 `rev` 與新的原文，頁面接著用。
- **編輯表單也帶 `rev`**：產出沒有反芻期，會長期修改。兩台裝置都開著編輯頁時，舊的那頁一存，就會無聲蓋掉另一頁存下的內容；在卡片頁勾過的項目也一樣。`GET /c/:id/edit` 帶上 `rev`，`PUT /c/:id` 與現況不符回 409；前端保留表單內容與草稿，提示重新載入。它只在存檔時提醒，不合併兩邊的內容。沒帶 `rev` 的請求（API、測試）不檢查。
- **碎片**：文字存在 `title`（v2 A.5），勾選改的是 `title`。讀寫一律經過 `cardText` 與 `withCardText`（`domain/card.ts`），不自己判斷那段文字在哪個欄位。
- **寫入**：沿用既有的寫入路徑（寫檔、更新索引、一個 commit），commit 訊息為 `check {id}`。
- **介面**：只有卡片頁可以勾；列表摘要與來源對照面板不提供。沒有 JavaScript 時核取方塊唯讀。
- **複製與下載**：交出去的原文照樣帶著 `[x]`。

### 2.4 與 TODO 習慣的對應

每天一張卡。當天在反芻期內增刪項目，做完的勾掉；過了反芻期，項目不能再改，但仍然可以勾。

## 3. 新型別：產出

### 3.1 定義

產出是做出來的成品的紀錄：寫成的文章、故事、報告等。思考記錄的是主張與推論，產出記錄的是成品。

v2 A.1 的型別表加一列：

| type | UI 標籤 | 對誰負責 | 錯的方式 | 修法 |
|---|---|---|---|---|
| `output` | 產出 | 對成品本身負責 | 沒有做成想要的樣子 | 改稿；被引用之後發新版本 `updates` |

思考問「這是真的嗎」，產出問「這是我要的樣子嗎」。成品不提出命題，所以 `supports`、`refutes`、`contradicts` 對它沒有意義。

型別 ID 為 `output`。它寫進卡片檔之後就改不掉（v2 D.3）。

### 3.2 不設反芻期

**R15. `output` 不設反芻期：被引用（R6）之前，修改、新增連結（R7）與刪除（R9）都不受時間限制。**

- 產出需要反覆改稿。反芻期一過就只能發新版本的話，每改一次就多一張卡。
- 定案照舊由 R6 決定，只看 frontmatter 的 `links`。應用程式產生的段落連結只有一個來源：來源面板的「引用」鈕，而那條路徑一定帶著指回同一張卡、拿不掉的連結（v2 C.3、R7），所以都在 R6 的保護範圍內。不受保護的只剩手動貼進正文的網址；需要穩定的錨點時，建立連結。
- 連結照舊只增不減（R7）。改稿時用上新的材料，隨時可以補上取材的連結。加錯的連結，在被引用之前都可以整張刪掉重建；代價是新卡換了 ID 與建立時間。
- 修改視同建立的一部分（R4）：不論何時修改，都要通過當下的現行規則。

連帶的變化：

- **沉澱清單不列產出**：沉澱是「還在反芻期內」的卡片，產出沒有反芻期。
- **卡片頁與編輯頁不顯示反芻倒數**：編輯頁改為一行說明「被引用之前都可以修改」。
- **`ruminationOf` 多收型別**：未被引用的產出，回答「開著，沒有期限」。`Rumination` 的 `until` 因此可以是空的。

### 3.3 欄位

- 標題、內文、標籤、連結，與 `thinking` 相同。`url`、`provenance`、`source_*` 為 `null`（v2 A.5）。
- 標籤不強制（§4.1）。

### 3.4 關係矩陣

v2 A.3 加入：

| 來源 type | rel | 目標 type | 核心意圖 |
|---|---|---|---|
| `output` | `updates` | `output` | 新版本取代舊版本 |
| `output` | `related` | 任意 | 取材：這份產出從哪些材料與想法長出來 |
| `thinking` | `about` | `original` / `restatement` / `output` | 加上 `output`：這則思考在討論這份產出 |

- `thinking` 的 `related` 目標本來就是任意型別，自動涵蓋 `output`。
- 其餘型別不能指向 `output`。
- 介面用字沿用既有的 rel，不新增。

**修訂 v2 A.3「`related` 只開放給 `thinking`」**：開放給 `output`。那一條的理由是 `related` 若每一型都能用，會變成逃避定義關係的逃生口；這對產出不成立，產出與取材對象之間沒有更精確的關係可選。

### 3.5 建立入口

- **隨手記的「展開」**：完整表單上在思考與產出之間二選一，預設思考（§4.3）。沒有來處的產出從這裡建立，側欄不設入口。
- **卡片頁的 `+`**（v2 C.3），新增的動作：

  | 當前卡片 | 按鈕 | 建立 | rel |
  |---|---|---|---|
  | `thinking`、`fleeting` | 建立產出 | `output` | `related` |
  | `output` | 更新 | `output` | `updates` |
  | `output` | 發想 | `thinking` | `about` |

  按鈕在各選單中的位置由使用者排定（`CARD_ACTIONS` 的順序是有意義的）。標籤照 v2 C.3 自動繼承。
- **手動連結列的預設 rel**（v2.2 §5）：`related`。

### 3.6 呈現

- **色點**：偏紅，`#D16E8F`（OKLCH L 0.66 / C 0.13 / h 0°）。第一版 `#BE6877`（L 0.62 / C 0.11 / h 10°，與藍綠對齊）實看跟思考的棕色太近，兩個都是偏灰的暖色；改成明度與思考相同、彩度高一階、色相往玫瑰紅轉。OKLab 色差：對思考 0.127 → 0.147，對 `--alert`（`#B4483F`，只用在錯誤訊息與刪除鈕）0.090 → 0.134。
- **列表 meta 行**（U5）：比照 `thinking`，即 `產出 · 出向 N · 入向 M`。
- **首頁篩選列與搜尋的型別篩選**：多一個選項，由 `CARD_TYPES` 產生，前方照樣附色點（U7）。

### 3.7 既有卡片

已經寫成 `thinking` 的產出維持原樣（v2 D.3 型別不可改、R4 不追溯）。要歸到產出，就發一張 `output` 以 `related` 指回；或者手動改檔，再用側欄的「更新」取回（§7）。手動改型別繞過了 D.3，被牽動的連結若因此違反矩陣，重建報告會列出來（R4）。

## 4. `thinking` 需要標籤

### 4.1 規則

**R11. `thinking` 至少需要一個標籤；其餘型別不強制。**

- `fleeting`：碎片的價值在於零決策輸入。碎片被完整化成 `thinking` 時，標籤自然補上。
- `original`：沒有脈絡可以繼承，強制的成本最高。
- `restatement`：依 R1 錨定原文，脈絡已經由原文提供。
- `output`：常從隨手記展開建立，沒有可以繼承的標籤，處境與 `original` 相同。

強制的成本由標籤繼承壓低：從卡片頁 `+` 衍生的 `thinking` 自動帶入來源卡的標籤（v2 C.3）。

### 4.2 不追溯

- 既有的無標籤 `thinking` 維持原樣，重建索引時列入警告清單（R4）。
- 反芻期內的修改視同建立：不能把標籤刪到一個不剩。

### 4.3 隨手記只寫碎片（與 R11 同批上線）

隨手記移除標題欄位，只建立碎片。要記成思考或產出，就按「展開」進入完整表單，那裡有標籤欄與推薦列。

- **理由**：隨手記原本「填了標題就是思考」（v2 C.2），而那張表單沒有標籤欄，R11 上線後這條路徑會被擋下。移除標題欄是最小的改動，R11 不必在隨手記另外處理；入口的意圖也一致——隨手記是碎片的入口，思考與產出一律走完整表單。
- **「展開」**：隨手記裡的文字帶進完整表單的內文。型別在思考與產出之間二選一，預設思考，表單標題是「展開成思考或產出」。型別按鈕的名字前面放同一顆色點（U7 的語彙）；裸的 `/new` 的型別選單共用同一個樣式，也一樣。兩型的欄位一樣，差別只在錯的時候怎麼修——那是寫到需要展開時才判斷得出來的事，所以在完整表單上選。
- **退回時照樣二選一**：表單帶著 `entry=expand` 送出，驗證失敗重新渲染時型別仍然可選。思考因為沒有標籤被擋下來時，改成產出正是一條出路。
- **草稿槽**：沿用 `new:thinking:expand`。它認的是「展開」這個入口，不是型別。
- **`?tag=` 篩選的自動帶入保持原樣**（v2.2 §6）：隨手記的標題顯示「隨手記 · #標籤名」，送出時帶上那個標籤；展開時填進標籤欄，可以自由修改。
- **U18 撤回**：隨手記只會存成碎片，沒有要顯示的判斷。送出鈕固定為「記為碎片」。
- **`POST /quick` 只建立碎片**：不再讀 `title`，內文經 `fleetingDraft` 存進 `title`（v2 A.5）。
- **舊草稿**：`quick` 槽裡的標題不再還原。

## 5. 側欄下半依頁面切換：最近的標籤或最近的卡片

側欄下半原本是卡片索引：最近的卡片，用來在建立連結時查名稱（v2 B.3、U11）。舊草案要把它整個換成標籤清單，前置條件是 `v2.2 草稿暫存` → `連結列行內選卡器（快速搜尋引用）` → `側欄卡片索引替換為標籤清單`；前兩項都已完成（連結列打標題就會搜尋，`/api/search`，2026-09-06 起）。

整個換掉之後，讀卡、寫卡時少了一眼就看得到的名字。所以改成依頁面切換：

| 頁面 | 側欄下半 | 理由 |
|---|---|---|
| 文章一覽：首頁、搜尋、標籤頁、各份清單、更新的結果頁 | 最近的標籤 | 在一覽裡找方向，主題是入口 |
| 卡片頁與編輯介面：卡片頁、編輯頁、建立表單（含隨手記展開之後） | 最近的卡片 | 要連到哪一張才是問題，看一眼名字就知道 |

- **最近的標籤**：與表單的標籤推薦是同一份清單——依最近使用排序，與標籤頁的預設排序一致（§6.2）；不列鎖定的標籤（v2.2 §7.2），出處標記不是主題。點一個開 `/?tag=`；首頁的篩選生效時，那一個標起來。
- **最近的卡片**：建立時間最近的 20 張，色點加標題（U11 的形式，不放型別名）。正在看或正在改的那一張標起來。
- **呈現**：小標「最近的標籤」或「最近的卡片」，只列名稱、不列數量；太長的名稱截斷。清單是空的時候整塊不出現。
- **錯誤與訊息頁**（找不到、已鎖定）沿用預設，列最近的標籤。

## 6. 介面調整

### 6.1 Markdown 檔下載

卡片頁的複製鈕旁邊加一顆下載鈕，把卡片存成 `.md` 檔。把內容交給 AI 發想時，直接給檔案比貼上剪貼簿方便。

- **內容**：`# {標題}`、一個空行、內文。碎片只有它那段文字（v2 A.5）。
- **來源**：內文用 `.body[data-md]`（v2.2 §4）；標題由模板另外印在 `data-title` 上，不從畫面上的標題反解析。前端產生檔案（`public/js/download.js`），不新增路由。
- **檔名**：`{標題}.md`；碎片沒有標題，用 `{id}.md`。標題裡檔名不允許的字元交給瀏覽器替換，例如「A/B 測試」存成「A_B 測試.md」。
- **位置與圖示**：與複製鈕並列在 meta 行末；`icon.eta` 補一個 `download` 圖示。

### 6.2 標籤頁預設排序改為最近使用

`/tags` 的預設排序由「數量」改為「最近使用」，方便檢視最近在想什麼。三個分頁都保留，順序改為：最近、數量、名稱。v2.2 §8 的表改為：

| `?sort=` | 排序規則 | 說明 |
|---|---|---|
| （預設）／`recent` | `last_used DESC, tag ASC` | 依最近使用時間排序 |
| `count` | `n DESC, tag ASC` | 依卡片數量由多至少 |
| `name` | `tag ASC` | 依名稱碼位排序 |

- **改動**：`routes.ts` 的預設值與分頁順序；`tags.eta` 判斷「哪一個分頁不帶 `?sort=`」的那一行；斷言「索引頁預設按數量」的測試。
- 表單的標籤推薦原本就按最近使用，不受影響。

### 6.3 碎片編輯頁修正（已完成）

碎片送出後再編輯，整段文字會擠進單行的標題欄，換行被瀏覽器丟掉，一存檔就壓成一行。已修正：碎片的編輯頁與建立表單一致，只有一個大文字框。已經被壓成一行的舊碎片沒有修復，原文要從 git 歷史取回。

## 7. 側欄「更新」：取回語料庫的最新版本

版本更改的時候，卡片檔可能需要手動調整：在別處的語料庫 clone 裡改好、push 上去。「更新」把這些結果拉回伺服器，並重建索引。

### 7.1 介面

- 側欄的動作與工具依序是：追加外部資料、搜尋、標籤、更新。「更新」是一顆送出 `POST /update` 的按鈕，外觀與側欄其他項目相同；不做成連結，因為 GET 不該有副作用。
- 結果頁說明這次發生了什麼：已是最新、取回了哪些 commit（`git log --oneline 舊HEAD..FETCH_HEAD`：遠端那一份裡本機原本沒有的。本機還沒推上去、被 rebase 重寫的 commit 不算在內），或失敗的原因；以及重建報告（筆數、讀不出來的檔案、壞連結、規則警告）。
- 名稱與卡片頁 `+` 選單的「更新」相同，但兩者不會出現在同一個地方。

### 7.2 流程

1. 排進 `GitBackup` 的佇列，與 commit、push 走同一條 promise chain，等前面的操作做完。
2. 補上還沒 commit 的卡片（`commitPendingCards`）。
3. `git pull --rebase`。有衝突就 `git rebase --abort`，語料庫回到原狀，回報衝突的檔案，不重建索引。
4. 本機有領先遠端的 commit 就 push。
5. 重建索引，與 `POST /_reindex` 相同。

- **不是 git repository、或沒有 remote**：跳過 2–4，只重建索引。直接在伺服器上改檔的情況也用得到。
- **會等 git 做完才回應**，不是 fire-and-forget。pull 加上逾時，逾時視同失敗：它走的是備份共用的那條佇列，卡住會擋住之後所有的 commit 與 push。卡片的寫入路徑不受影響（MVP I5）。
- **用 `--rebase` 而不是 `--ff-only`**：push 失敗時，本機會有還沒推上去的卡片 commit，`--ff-only` 會在這時候拒絕；rebase 只重寫那些還沒推上去的 commit。

### 7.3 手動調整的範圍

手動改檔可以繞過應用程式的規則，例如改型別、改已定案的卡。這是刻意留的出口：改版時的資料調整由使用者自己負責。重建報告會列出因此違反現行規則的卡片（R4）與壞掉的連結。

`tags.yml` 也在語料庫裡（v2.2 §7.2），同一個動作會一起取回。

### 7.4 改動檔案

| 檔案 | 改動 |
|---|---|
| `src/store/backup.ts` | `pull()`：走同一條佇列、可以等待、回報結果（`PullResult`） |
| `src/service/update.ts`（新檔） | 更新的流程：取回之後重建 |
| `src/web/routes.ts`、`src/web/present.ts`（`updateView`）、`src/web/views/update.eta`（新檔） | `POST /update` 與結果頁 |
| `src/web/views/layout.eta`、`icon.eta`、`public/css/shell.css`、`list.css` | 側欄的「更新」按鈕與圖示；結果頁的樣式 |
| `test/` | 已是最新、取回新 commit、本機領先的 commit 接在後面再推上去、衝突時回到原狀、沒有 git 時只重建 |

## 10. 核心裁決紀錄（G 節補充）

1. **否決為個別流程做專屬功能。** 流程是習慣，還會變；機制只提供原件。
2. **勾選是狀態，不是修改**（R14）。
3. **否決「一張卡一件待辦、以連結標記完成」。** 待辦的單位是一則內文裡的條列，不是一張卡一件事。
4. **產出從思考分出來，成為獨立型別**（§3）。判準沿用「錯的時候該怎麼修」；名稱用比「創作」泛用的「產出」。
5. **產出不設反芻期**（R15）。定案只看 R6。
6. **`related` 開放給產出**（§3.4）。產出與取材對象之間沒有更精確的關係可選，它在這裡不是逃生口；否決新增專用的「取材」關係。
7. **隨手記只寫碎片**（§4.3）。思考與產出一律走完整表單：R11 不必在隨手記另外處理，入口的意圖也一致。展開之後才在思考與產出之間選，產出因此不另設側欄入口。
8. **反芻期暫時保留。** 產出以外的修改期限移到 v3.1 草案。
9. **維持 v2 G 節「否決正文引用參與定案鎖定」**（§3.2）。應用程式產生的段落連結都帶著結構化連結，R6 已經涵蓋；只為手動貼上的網址多一張索引表與一套解鎖語意，不划算。
10. **「更新」衝突就放棄**（§7.2）。不在伺服器上解衝突；衝突在別處的 clone 裡解決之後再取回。
11. **側欄下半依頁面切換，不整個換掉**（§5）。舊草案把卡片索引整個換成標籤清單；但讀卡、寫卡時要的是一眼看得到的名字，選卡器要先打字才找得到。所以一覽頁列標籤，卡片頁與編輯介面列卡片。
