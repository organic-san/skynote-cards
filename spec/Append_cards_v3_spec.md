## 1. 版本定位

v2 的設計假設是「單一主題、長脈絡的深入思考」；實際用法是「把想法連起來，做短脈絡的延伸」（草案 2 §1）。v3 依循一條原則：**機制只提供原件，流程留在使用習慣裡。**

本版做四件事：

1. **補一個原件：勾選**（§2）。
2. **拿掉文字修改的時間限制**（§3）。文字只在被依賴之後才不可變；連結與刪除仍然只限反芻期內。
3. **把產出從思考分出來**（§4）。
4. **延續舊草案的兩項，加上三項介面調整**（§5–§7）。

## 2. 待辦勾選

### 2.1 語法

`[ ]`（未完成）與 `[x]`（完成，`[X]` 同義）渲染成可以點的核取方塊。標記必須在清單項目的開頭：

```markdown
10/7
- [ ] 09:00 交作業
- [x] 買車票
1. [ ] 也可以用編號清單
```

行首沒有清單記號的 `[ ] 事情` 不是標記。這與 GitHub 及其他 Markdown 工具的寫法一致，下載的 `.md`（§7.1）拿到別處仍然是待辦清單。

### 2.2 規則

**R14. 切換勾選標記不算修改卡片，不受反芻期（R5）與定案（R6）限制。**

- **不算修改**：不可變的意義在於寫完不必回頭維護，不在於禁止狀態改變。勾選記錄的是「這件事做完了」，不是內容的修訂。
- **不牴觸 R6**：R6 守護段落錨點 `#b{n}`。切換一個字元不改變區塊的數量與順序，錨點照舊有效。
- §3 之後，未被引用的卡片本來就能改。R14 實際作用的是兩件事：被引用的卡片仍然可以勾，以及勾選不更新 `revised`。

邊界：

1. 一次請求只改一個標記，只在 `[ ]` 與 `[x]` 之間互換。**除了那一個字元，檔案內容逐位元相同。**
2. 新增或刪除項目、修改項目的文字，是編輯，受 §3 的限制。
3. 勾選不更新 `revised`。變更留在 git 歷史裡。
4. 勾選不改變反芻狀態，不影響沉澱清單。

### 2.3 實作

- **渲染**：`render.ts` 加一條 markdown-it 規則，做法比照 `block_anchor`：清單項目開頭的標記換成核取方塊，依出現順序給 `data-task="k"`（從 0 起）。
- **定位**：伺服器以渲染器自己的解析結果（token 的來源行號）找出原文裡第 k 個標記，不另寫正規表示式。程式碼區塊裡的 `- [ ]` 不是標記，兩套判斷遲早會對不上。
- **端點**：`POST /c/:id/tasks/:k`，內容為 `{ "checked": true, "rev": "…" }`。`rev` 是頁面載入時那段文字（碎片是 `title`，其餘是 `body`）的雜湊；與現況不符回 409，前端重新載入。
- **編輯表單也帶 `rev`**：編輯頁送出的是整份內文，開著編輯頁時在卡片頁勾過，一送出就會蓋掉那次勾選。`GET /c/:id/edit` 帶上 `rev`，`PUT /c/:id` 與現況不符回 409；前端保留表單內容與草稿，提示重新載入。
- **碎片**：文字存在 `title`（v2 A.5），勾選改的是 `title`。讀寫一律經過 `fleetingText` 與 `fleetingDraft`。
- **寫入**：沿用既有的寫入路徑（寫檔、更新索引、一個 commit），commit 訊息為 `check {id}`。
- **介面**：只有卡片頁可以勾；列表摘要與來源對照面板不提供。沒有 JavaScript 時核取方塊唯讀。
- **複製與下載**：交出去的原文照樣帶著 `[x]`。

### 2.4 與 TODO 習慣的對應

每天一張卡，做完的勾掉。被引用之前，項目可以隨時增刪（§3）；被引用之後，項目不能再改，但仍然可以勾。

## 3. 未被引用的卡片可以一直修改

### 3.1 規則

**R5（修訂）. 卡片自建立起有一段反芻期，長度由 `EDIT_WINDOW_HOURS` 決定，預設 8 小時。反芻期只管連結的新增（R7）與刪除（R9）；文字欄位的修改不受反芻期限制，只受 R6 限制。**

時間限制對修正小錯誤與補述的意義不大。需要保護的是被依賴的東西，而那由 R6 負責：被指向就定案。

v2 D.3 的修改約束改為：

| | 反芻期內、未被指向 | 反芻期後、未被指向 | 被指向（R6） |
|---|---|---|---|
| `title` `body` `tags` `url` `provenance` `source_*` | 可改 | 可改 | 不可改 |
| `links` | 只增不減（R7） | 不可新增 | 不可新增 |
| 刪除整張卡（R9） | 可以 | 不可以 | 不可以 |
| `type` `id` `created` | 不可改 | 不可改 | 不可改 |

連結與刪除留在反芻期內：

- **刪除是連結的配套**（v2 D.4）。連結選錯收不回，只能整張刪掉重建，所以連結能加的期間必須也能刪。
- **反芻期後的關聯是新的思考**（MVP I4）。要把舊卡連到更舊的卡，發一張新卡同時指向兩者。
- **刪除比修改重。** 刪除讓正文裡的 `/c/{id}` 變成死連結；手滑通常當下就會發現。

**R4 的但書**由「反芻期內的修改視同建立的一部分」改為「修改視同建立的一部分」：不論何時修改，都要通過當下的現行規則。規則收緊之後，修改一張不合新規則的舊卡，要在同一次修改裡讓它合規（例如 §5.2）。

### 3.2 連帶的變化

- **判準拆成兩個**：「文字能不能改」只看 R6；「連結與刪除能不能動」看 R5 與 R6。`ruminationOf` 一次回答兩者，路由、模板與寫入路徑問的是同一份答案。
- **沉澱清單**：定義不變（反芻期內且未被指向）。它的意思變成「還能補連結、還能刪除的卡」，空狀態的文字改為說反芻期，不再說「可修改時間」。
- **卡片頁**：meta 行末尾的「尚可編輯 N 小時」（v2 D.5）移除。「編輯」鈕的判準改為「沒有被指向」。
- **編輯頁**：403 只在被指向時發生。倒數改說連結與刪除的期限（例如「連結與刪除還剩 3 小時」）；反芻期後，新增連結的區塊與刪除鈕不出現，換成一行說明。
- **鎖定訊息**：只剩被指向一種原因，`LOCKED_MESSAGE` 改為說明「這張卡已被引用」。
- **`revised`**：每次修改照舊更新。

### 3.3 已知風險：正文引用

v2 G 節否決了「正文引用參與定案」：只有 frontmatter 的 `links` 會讓目標定案。以前時間一到所有卡片都會定案，這個缺口只開 8 小時；現在只被正文引用的卡片會一直可改，段落錨點可能位移。

接受這個風險。小修正與補述通常不改變區塊的數量與順序；需要穩定的錨點時，用結構化連結引用。實際出現腐爛時，重新評估 G 節那一條。

|---|---|

| `src/service/cards.ts` | `updateCard` 的鎖定只看 R6，`addLinks` 另外檢查反芻期；`deleteCard` 不變 |

## 4. 新型別：創作（暫名）

> 名稱待定。候選：創作、作品、產出；`work`、`piece`。定名之前本節不得實作。

### 4.1 定義

創作是產出類型的文章紀錄，例如寫成的故事或文章。思考記錄的是主張與推論，創作記錄的是產出。

v2 A.1 的型別表加一列：

| type | UI 標籤 | 對誰負責 | 錯的方式 | 修法 |
|---|---|---|---|---|
| `work` | 創作 | 對作品本身負責 | 沒有寫成想要的樣子 | 改稿；被引用之後發新版本 `updates` |

思考問「這是真的嗎」，創作問「這是我要的樣子嗎」。作品不提出命題，所以 `supports`、`refutes`、`contradicts` 對它沒有意義。

作品在被引用之前可以一直改稿（§3）；被引用之後，以新版本延續。

### 4.2 欄位

- 標題、內文、標籤、連結，與 `thinking` 相同。`url`、`provenance`、`source_*` 為 `null`（v2 A.5）。
- 標籤不強制（§5.1）。

### 4.3 關係矩陣

v2 A.3 加入：

| 來源 type | rel | 目標 type | 核心意圖 |
|---|---|---|---|
| `work` | `updates` | `work` | 新版本取代舊版本 |
| `work` | `related` | 任意 | 取材：作品從哪些材料與想法長出來 |
| `thinking` | `about` | `original` / `restatement` / `work` | 加上 `work`：這則思考在討論這篇作品 |

- `thinking` 的 `related` 目標本來就是任意型別，自動涵蓋 `work`。
- 其餘型別不能指向 `work`。
- 介面用字沿用既有的 rel，不新增。

**修訂 v2 A.3「`related` 只開放給 `thinking`」**：開放給 `work`。那一條的理由是 `related` 若每一型都能用，會變成逃避定義關係的逃生口；這對作品不成立，作品與取材對象之間沒有更精確的關係可選。

### 4.4 建立入口

- **側欄**：「追加外部資料」下方加「新增創作」，開 `/new?type=work`，表單標題同名（U14、`ENTRY_TITLE`）。
- **卡片頁的 `+`**（v2 C.3），新增的動作：

  | 當前卡片 | 按鈕 | 建立 | rel |
  |---|---|---|---|
  | `thinking`、`fleeting` | 寫成創作 | `work` | `related` |
  | `work` | 更新 | `work` | `updates` |
  | `work` | 發想 | `thinking` | `about` |

  按鈕在各選單中的位置由使用者排定（`CARD_ACTIONS` 的順序是有意義的）。標籤照 v2 C.3 自動繼承。
- **手動連結列的預設 rel**（v2.2 §5）：`related`。
- **隨手記不變**：填了標題仍然是 `thinking`（v2 C.2）。

### 4.5 呈現

- **色點**：實心紫，起點 `#A36FAF`（OKLCH L 0.62 / C 0.11 / h 320°），與既有四色及 `--alert` 的紅拉開色相；實作時依 U27 校正，校正後的值回填本節。

## 5. `thinking` 需要標籤

### 5.1 規則

**R11. `thinking` 至少需要一個標籤；其餘型別不強制。**

- `fleeting`：碎片的價值在於零決策輸入。碎片被完整化成 `thinking` 時，標籤自然補上。
- `original`：沒有脈絡可以繼承，強制的成本最高。
- `restatement`：依 R1 錨定原文，脈絡已經由原文提供。
- `work`：常從側欄的全域入口建立，沒有可以繼承的標籤，處境與 `original` 相同。

強制的成本由標籤繼承壓低：從卡片頁 `+` 衍生的 `thinking` 自動帶入來源卡的標籤（v2 C.3）。

### 5.2 不追溯

- 既有的無標籤 `thinking` 維持原樣，重建索引時列入警告清單（R4）。
- 修改視同建立（§3.1）：不能把標籤刪到一個不剩；沒有標籤的舊 `thinking` 被修改時，要補上標籤才能儲存。

### 5.3 隨手記的標籤欄（與 R11 同批上線）

隨手記填了標題就是 `thinking`（v2 C.2），而那張表單沒有標籤欄，只在 `?tag=` 篩選生效時以隱藏欄位帶入一個（v2.2 §6）。R11 上線後這條路徑會被擋下，所以同批處理：

- **標題欄第一次有字時，展開標籤欄與推薦列**，與完整表單共用 `tags.js` 與推薦清單（v2.2 §7）。展開後不再收起：收起會讓已經填的標籤看不見卻照樣送出。
- **`?tag=` 生效時**，帶入的標籤就是這一欄的初始值。欄位還沒展開時照樣送出它的值，即 v2.2 §6 現行的行為。
- **U18 的提示**：標題有字、標籤欄是空的時候，改說「將存為 思考 · 需要標籤」。
- **送出時仍然沒有標籤**：伺服器依 R11 退回（400），面板顯示錯誤，草稿保留（v2.2 §2.2）。

## 7. 介面調整

### 7.1 Markdown 檔下載

卡片頁的複製鈕旁邊加一顆下載鈕，把卡片存成 `.md` 檔。把內容交給 AI 發想時，直接給檔案比貼上剪貼簿方便。

- **內容**：`# {標題}`、一個空行、內文。碎片只有它那段文字（v2 A.5）。
- **來源**：內文用 `.body[data-md]`（v2.2 §4）；標題由模板另外印在 `data-title` 上，不從畫面上的標題反解析。前端產生檔案，不新增路由。
- **檔名**：`{標題}.md`。碎片，或標題含 `/ \ < > : " | ? *` 與控制字元時，退回 `{id}.md`。
- **位置與圖示**：與複製鈕並列在 meta 行末；`icon.eta` 補一個 `download` 圖示。

### 7.2 標籤頁預設排序改為最近使用

`/tags` 的預設排序由「數量」改為「最近使用」，方便檢視最近在想什麼。三個分頁都保留，順序改為：最近、數量、名稱。v2.2 §8 的表改為：

| `?sort=` | 排序規則 | 說明 |
|---|---|---|
| （預設）／`recent` | `last_used DESC, tag ASC` | 依最近使用時間排序 |
| `count` | `n DESC, tag ASC` | 依卡片數量由多至少 |
| `name` | `tag ASC` | 依名稱碼位排序 |

- **改動**：`routes.ts` 的預設值與分頁順序；`tags.eta` 判斷「哪一個分頁不帶 `?sort=`」的那一行；斷言「索引頁預設按數量」的測試。
- 表單的標籤推薦原本就按最近使用，不受影響。

### 7.3 碎片編輯頁修正（已完成）

碎片送出後再編輯，整段文字會擠進單行的標題欄，換行被瀏覽器丟掉，一存檔就壓成一行。已修正：碎片的編輯頁與建立表單一致，只有一個大文字框。已經被壓成一行的舊碎片沒有修復，原文要從 git 歷史取回。

未採納：在編輯頁為碎片補標題、使它升格為 `thinking`（需要鬆動 v2 D.3「型別不可改」）。

## 10. 核心裁決紀錄（G 節補充）

1. **否決為個別流程做專屬功能。** 流程是習慣，還會變；機制只提供原件。
2. **勾選是狀態，不是修改**（R14）。
3. **否決「一張卡一件待辦、以連結標記完成」。** 待辦的單位是一則內文裡的條列，不是一張卡一件事。
4. **文字修改的限制只剩因果**（§3）。文字隨時能改，被指向才定案。
5. **連結與刪除維持反芻期**（§3.1）。否決「全部不設期限」：反芻期後加錯的連結只能整張刪掉重建，舊卡會失去它的 ID 與在時間軸上的位置。
6. **產出從思考分出來，成為獨立型別**（§4）。判準沿用「錯的時候該怎麼修」。
7. **`related` 開放給作品**（§4.3）。作品與取材對象之間沒有更精確的關係可選，它在這裡不是逃生口；否決新增專用的「取材」關係。
8. **隨手記的標籤入口用欄位，不用跳頁**（§5.3）。正常的送出不該看起來像被退件。
9. **接受正文引用的錨點可能位移**（§3.3）。需要穩定錨點時用結構化連結；G 節「否決正文引用參與定案」維持。
