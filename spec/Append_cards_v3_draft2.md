## 1. 背景：為什麼是這個方向

### 1.1 設計假設與實際用法的落差

v2 的設計假設是「單一主題、長脈絡的深入思考」：資料進來、重述、形成思考，三份待處理清單負責提醒哪些東西還沒被接住。

實際的用法是另一種：**把想法連起來，做短脈絡的延伸**。思緒很快，而且是網狀擴張，反覆編修一份文件的方式並不適合。由此得到三個觀察：

1. **跨分野的雜訊。** 首頁是一條混著所有主題的時間軸，不同脈絡的內容互相干擾。這一項由 v3.1 草案的環境回應。
2. **離開 Discord 只完成一部分。** Skynote 的另一個目的是取代 Discord 作為個人紀錄的地方。目前只有「發想與思辯」搬過來，其餘仍在 Discord（見 §1.2）。
3. **不可變的價值在放鬆，不在限制。** 寫完就不必回頭維護，這是它有意義的地方。它不是一項硬性需求，而是從「通常不會回頭編輯舊內容」推導出來的可行用法。勾選（§2）與修改期限（§3）都從這一點出發。

### 1.2 還留在 Discord 的使用方式

下表記錄的是目前的習慣，不是定型的流程，日後還會變。

| 方式 | 做法 | 以 Skynote 現有機制表達 | 缺口 |
|---|---|---|---|
| TODO | 每天開一則新訊息；當天之內在同一則增刪；完成的按表情標記 | 一張卡加上反芻期 | 一個放的地方；標記完成 |
| 紀錄 | 有情報就往裡面丟 | 隨手記 | 一個放的地方 |
| 想做的事 | 想到就丟；不定期發一則整理目前狀況的訊息 | 隨手記；整理就是一張新卡 | 一個放的地方 |
| 進度控管 | 一則母訊息，加上每天的進度更新 | 母卡，加上連回它的子卡；下游串即時間軸 | 母卡被引用後就定案，無法再補充（§8） |
| 規劃 | 情報、時程、待辦、考量混在一起 | 暫無對應 | 目前沒有搬遷的需求（§8） |
| 旅遊紀錄 | 同一處混用 TODO 與紀錄 | 同上兩列 | 一個放的地方 |

幾乎每一列缺的都是同一樣東西：**一個放的地方**。這由 v3.1 草案的環境回應；本文件處理的是「標記完成」。

### 1.3 設計原則

**機制只提供原件，流程留在使用習慣裡。**

上表的每一種方式，在 Discord 裡都不是功能，而是習慣。Discord 只提供幾個原件：一個地方、發一則、短時間內改一則、按一個表情。流程是在上面長出來的，所以自由，也所以還能繼續變。

v2 走的是相反的路：它把一套流程（資料、重述、思考，加上 rel 矩陣）寫成規則，而那套流程與實際用法對不上。把上表逐項做成功能，會重演同一個問題，而且會得到互不一致的規則。

v3 因此只補兩個原件：**勾選**（§2）與**環境**（v3.1 草案）。本文件另外兩項不是新原件，而是調整既有的機制：§3 拿掉修改的時間限制，§4 把產出從思考裡分出來。

## 2. 待辦勾選

### 2.1 語法【已定，寫法待確認】

支援 `[ ]`（未完成）與 `[x]`（完成，`[X]` 同義），渲染成可以點的核取方塊。

標記必須在清單項目的開頭【待確認】：

```markdown
10/7
- [ ] 09:00 交作業
- [x] 買車票
1. [ ] 也可以用編號清單
```

要求清單項目，是為了與 GitHub 及其他 Markdown 工具的寫法一致：下載的 `.md`（§7.1）拿到別處仍然是待辦清單。行首沒有清單記號的 `[ ] 事情` 不視為標記。

### 2.2 規則

**R14（候選）. 切換勾選標記不算修改卡片，任何時候都可以切換。**

勾選不受反芻期（R5）限制【已定】，也不受定案（R6）限制【待確認】。

- **為什麼不算修改**：不可變的意義在於寫完不必回頭維護（§1.1），而不在於禁止狀態改變。勾選記錄的是「這件事做完了」，不是對內容的修訂。
- **為什麼不牴觸 R6**：R6 守護的是段落錨點 `#b{n}`。切換一個字元不改變區塊的數量與順序，所有錨點照舊有效。
- **與 §3 的關係**：§3 上線後，未被引用的卡片本來就能改，R14 實際作用的是兩件事：被引用而定案的卡片仍然可以勾，以及勾選不更新 `revised`。§3 還沒上線時，R14 也讓過了反芻期的卡片可以勾。兩種順序下 R14 的寫法都不必改。

為了不讓這條規則變成編輯的後門，邊界如下：

1. 一次請求只改一個標記，而且只在 `[ ]` 與 `[x]` 之間互換。**除了那一個字元，檔案內容逐位元相同。**
2. 新增或刪除待辦項目、修改項目的文字，仍然是編輯，受編輯的限制（現行為反芻期；§3 上線後為 R6）。
3. 勾選不更新 `revised`【待確認】，那個欄位記的是內容的修訂。變更仍然留在 git 歷史裡。
4. 勾選不改變反芻狀態，不會讓卡片重新出現在沉澱清單。

### 2.3 實作要點

- **渲染**：`markdown-it` 沒有內建這個語法。在 `render.ts` 加一條規則，做法比照既有的 `block_anchor`：把清單項目開頭的標記換成核取方塊，並依出現順序給序號 `data-task="k"`（從 0 起）。
- **定位**：伺服器要找出原文裡的第 k 個標記。定位必須使用渲染器自己的解析結果（token 的來源行號），不得另寫正規表示式——程式碼區塊裡的 `- [ ]` 不是標記，兩套判斷遲早會對不上。
- **端點**：`POST /c/:id/tasks/:k`，內容為 `{ "checked": true, "rev": "…" }`。`rev` 是頁面載入時那段文字的雜湊；與現況不符就回 409，前端重新載入。這擋的是另一個分頁改過內文、序號已經對不上的情況。
- **編輯表單也帶 `rev`**【待確認】：編輯頁送出的是整份內文。開著編輯頁的時候在卡片頁勾過，一送出就會把那次勾選蓋掉。編輯頁載入時一併帶上 `rev`，`PUT /c/:id` 與現況不符就回 409。§3 讓編輯不再有期限，這種交錯會更容易發生。
- **碎片**：碎片的文字存在 `title`（v2 A.5 的欄位反轉），勾選改的是 `title`。讀寫一律經過 `fleetingText` 與 `fleetingDraft`。
- **寫入**：沿用既有的寫入路徑，即寫檔、更新索引、一個 commit，commit 訊息為 `check {id}`。
- **介面**：只有卡片頁可以勾。列表摘要與來源對照面板不提供。沒有 JavaScript 時核取方塊顯示為唯讀。
- **複製與下載**：交出去的原文照樣帶著 `[x]`。

### 2.4 與 TODO 習慣的對應

每天一張卡，做完的勾掉。項目的增刪是編輯：現行只能在反芻期內；§3 上線後，只要還沒被引用都可以增刪。被引用之後項目不能再改，但仍然可以勾。

`EDIT_WINDOW_HOURS` 維持全域一個值，不為 TODO 另設長度。

## 3. 未被引用的卡片可以一直修改

### 3.1 動機【已定】

反芻期（R5，預設 8 小時）原本的用意，是留一段時間回頭審視與潤飾（v2 D.1）。實際用下來，這個期限對修正小錯誤與補述的意義不大。

檢查它實際保護了什麼：需要保護的是**被依賴的東西**，而那由 R6 負責——被指向的卡片，段落錨點 `#b{n}` 有人依賴，所以定案（v2 D.2）。沒有被指向的卡片，改了也不會讓任何結構化連結失效。時間限制在 R6 之外多擋下的，是對沒人依賴的卡片所做的修改，小修正與補述就屬於這一類。

這也與 §1.1 的第三點一致：不可變的價值在於寫完不必回頭維護，不在於禁止回頭。能改不等於要改。

### 3.2 規則【待確認】

**R5（修訂候選）. 卡片自建立起有一段反芻期，長度由 `EDIT_WINDOW_HOURS` 決定，預設 8 小時。反芻期只管連結的新增（R7）與刪除（R9）；文字欄位的修改不受反芻期限制，只受 R6 限制。**

v2 D.3 的修改約束改為：

| | 反芻期內、未被指向 | 反芻期後、未被指向 | 被指向（R6） |
|---|---|---|---|
| `title` `body` `tags` `url` `provenance` `source_*` | 可改 | 可改 | 不可改 |
| `links` | 只增不減（R7） | 不可新增 | 不可新增 |
| 刪除整張卡（R9） | 可以 | 不可以 | 不可以 |
| `type` `id` `created` | 不可改 | 不可改 | 不可改 |

連結與刪除留在反芻期內，理由有三：

- **刪除是連結的配套。** R9 存在是因為 R7：連結選錯收不回，只能整張刪掉重建（v2 D.4）。如果連結可以一直加、刪除卻只限反芻期，反芻期後加錯的連結就再也沒有補救的方法。兩者必須同一個期限。
- **反芻期後的關聯是新的思考。** 「發現兩個舊想法有關，本身就是一個新的思考，它應該有自己的節點」（MVP I4）。反芻期後要把舊卡連到更舊的卡，就發一張新卡同時指向兩者。
- **刪除比修改重。** 修改留下同一張卡，刪除讓它從語料庫消失，正文裡寫著 `/c/{id}` 的引用會變成死連結。手滑通常當下就會發現，反芻期足夠。

R4 的但書「反芻期內的修改視同建立的一部分，仍須通過當下的現行規則」改為「修改視同建立的一部分」：不論何時修改，都要通過當下的現行規則。規則收緊之後，修改一張不合新規則的舊卡，要在同一次修改裡讓它合規（例如 §5.1：沒有標籤的舊 `thinking`）。

### 3.3 連帶的變化【待確認】

- **判準拆成兩個**：「文字能不能改」只看 R6；「連結與刪除能不能動」看 R5 與 R6。
- **沉澱清單**：定義不變（反芻期內且未被指向，v2 B.1）。它的意思變成「還能補連結、還能刪除的卡」；文字隨時能改，所以它不再是「最後改得動的機會」。空狀態的文字「沒有任何卡片仍在可修改時間內」要跟著改。
- **卡片頁**：meta 行末尾的「尚可編輯 N 小時」（v2 D.5）移除。文字能不能改不再有期限，留著這個倒數，會讓人以為時間到了就不能改。「編輯」鈕照舊只在可改時出現，判準改為「沒有被指向」。
- **編輯頁**：倒數改說連結與刪除的期限，例如「連結與刪除還剩 3 小時」。反芻期後，新增連結的區塊與刪除鈕不再出現，換成一行說明。
- **鎖定時的訊息**：只剩被指向一種原因，`LOCKED_MESSAGE` 改成說明「這張卡已被引用」。
- **`revised`**：每次修改照舊更新。卡片頁的「改於」會比以前常出現，這是預期的。

### 3.4 代價與風險

**正文引用的段落錨點可能位移。** v2 G 節否決了「正文引用參與定案」：只有 frontmatter 的 `links` 會讓目標定案，正文裡寫的 `/c/{id}#b{n}` 不算。以前時間一到所有卡片都會定案，這個缺口只開 8 小時；§3.2 之後，只被正文引用的卡片會一直可改。

本草案接受這個風險【待確認】：

- 小修正與補述通常不改變區塊的數量與順序。改錯字不動區塊，補述多半接在最後。
- 需要穩定的錨點時，用結構化連結引用，它會讓目標定案。
- 實際出現腐爛時，再重新評估 G 節的那一條（§8）。

### 3.5 另一個做法：全部不設期限【待確認】

連結的新增與刪除也取消期限，「能不能動」只剩「有沒有被指向」一個判準。

- **好處**：規則只有一條，反芻期整個退場。
- **代價**：反芻期後加錯的連結只能整張刪掉重建，而重建會換掉 ID 與建立時間，對一張舊卡來說就是失去它在時間軸上的位置；舊卡可以一直刪，正文引用變成死連結的機會更大；沉澱清單要重新定義。

本草案建議 §3.2 的做法。

## 4. 新型別：創作（暫名）

### 4.1 定位【已定】

創作是產出類型的文章紀錄，例如寫成的故事或文章。它和思考的定位不同：思考記錄的是主張與推論，創作記錄的是產出。

依 v2 A.1 的判準「這張卡錯的時候該怎麼修」：

| type | UI 標籤 | 對誰負責 | 錯的方式 | 修法 |
|---|---|---|---|---|
| `thinking` | 思考 | 對世界負責 | 命題為假 | 換一個主張，發新的 thinking `updates` |
| `work`（暫名） | 創作（暫名） | 對作品本身負責 | 沒有寫成想要的樣子 | 改稿；被引用之後發新版本 `updates` |

思考問的是「這是真的嗎」，創作問的是「這是我要的樣子嗎」。把作品寫成 `thinking`，會讓兩種錯混在同一格；而作品不提出命題，`supports`、`refutes`、`contradicts` 對它也沒有意義。

名稱尚未決定（§10）。下文以「創作」與 `work` 暫稱。

### 4.2 為什麼是型別，不是標籤

- 型別決定錯的時候怎麼修，以及能用哪些關係（v2 A.1、A.3）。作品與思考在這兩點上都不同。
- 標籤的職責是主題普查（舊草案 §1）。用標籤標出「這是成品」，會讓同一個欄位同時表達主題與性質。

### 4.3 與 §3 的關係

作品需要反覆改稿。沒有 §3，反芻期一過，每改一次就得發一張新卡、用 `updates` 指回舊版。有了 §3，作品在被引用之前可以一直改；被引用之後（例如有一張思考在討論它），才以新版本延續。所以 §4 排在 §3 之後。

### 4.4 關係矩陣【待確認】

從 `work` 出發：

| rel | 目標 | 意圖 |
|---|---|---|
| `updates` | `work` | 新版本取代舊版本 |
| `related` | 任意 | 取材：這篇作品從哪些材料與想法長出來 |

指向 `work`：

- `thinking` 的 `related` 目標本來就是任意型別，加入新型別後自動涵蓋。
- `thinking` 的 `about` 目標加上 `work`【待確認】：這則思考在討論這篇作品，例如寫完之後的檢討。
- 其餘不開放：作品不提出命題，`supports`、`refutes`、`contradicts` 指向它沒有意義；`restatement` 依 R1 只錨定資料。

介面用字沿用既有的 rel，不新增。

**`related` 開放給 `work`，部分推翻 v2 A.3「`related` 只開放給 `thinking`」。** 那一條的理由是：`related` 是唯一弱語義的關係，每一型都能用的話，會變成逃避定義關係的逃生口。這對作品不成立——作品與取材對象之間本來就沒有更精確的關係可以選，`related` 不是在逃避哪一條。

另一個做法是新增一條專用的關係（例如「取材自」）。詞彙表、圖示（v2.2 §3）與介面用字都要跟著加，本草案不建議。

### 4.5 建立入口【待確認】

- **側欄「新增創作」**（暫名）：放在「追加外部資料」下方，開 `work` 的完整表單。作品常常不是從某一張卡衍生出來的，屬於 v2 C.2 所說「無任何參照的初始卡片」，需要一個全域入口。
- **卡片頁的 `+`**：
  - `thinking` 與 `fleeting` 加一顆「寫成創作」（暫名），建立 `work`，以 `related` 指回。想法寫成作品，是作品最常見的來處。
  - `work` 自己的選單：「更新」（建立 `work`，`updates`）與「發想」（建立 `thinking`，`about`；若 `about` 不開放給 `work`，改用 `related`）。
  - `original` 與 `restatement` 先不加，選單已經有四顆。
- **隨手記不變。** 填了標題仍然是 `thinking`（v2 C.2）。作品很少在一個浮動小框裡寫成。

### 4.6 欄位與呈現【待確認】

- **欄位**：標題、內文、標籤、連結，與 `thinking` 相同。`url`、`provenance`、`source_*` 為 `null`。發表處的網址，等到有需要再開。
- **標籤**：不強制（§5.1）。
- **色點**：第五個型別色。起點建議實心紫 `#A36FAF`（OKLCH L 0.62 / C 0.11 / h 320°），與藍（h 250°）、綠（h 153°）、琥珀（h 80°）以及 `--alert` 的紅（h 28°）都拉開色相；實作時依 U27 校正。U27「四個型別色是畫面上唯一的彩色」改為五個。
- **列表 meta 行**：比照 `thinking`，即 `創作 · 出向 N · 入向 M`。
- **首頁與搜尋的型別篩選**：多一個選項，由 `CARD_TYPES` 自動產生。

### 4.7 既有卡片

已經寫成 `thinking` 的作品維持原樣。型別不可改（v2 D.3），規則不追溯（R4）。要歸到創作，就發一張新的 `work`，以 `related` 指回；或者不搬。

## 5. `thinking` 需要標籤（沿用舊草案）

### 5.1 規則

**R11（候選）. `thinking` 至少需要一個標籤；其餘型別不強制。**

- **`fleeting` 必須維持免標籤**：碎片的價值在於零決策輸入，必填標籤會摧毀這個體驗。
- **`fleeting` 的缺口會自己補上**：碎片被完整化成 `thinking` 時，標籤自然補上。
- **`original` 與 `restatement` 不強制**：`original` 沒有脈絡可以繼承，強制的成本最高；`restatement` 依 R1 錨定原文，脈絡已經由原文提供。
- **`work` 不強制**：作品常從側欄的全域入口建立（§4.5），沒有可以繼承的標籤，處境與 `original` 相同。
- **不追溯**（R4）：既有的無標籤 `thinking` 維持原樣，重建索引時列入警告清單。修改視同建立（§3.2）：不能把標籤刪到一個不剩；沒有標籤的舊 `thinking` 被修改時，要補上標籤才能儲存。

### 5.2 與舊草案的差異

舊草案把 R11 與封閉詞彙表（R13）綁在同一批上線，由後者把強制的成本降成「從清單點選」。本文件不採納 R13，所以 R11 單獨成立，成本由卡片頁 `+` 的標籤繼承壓低：從卡片頁衍生的 `thinking` 會自動帶入來源卡的標籤（v2 C.3）。環境上線後，標籤推薦以環境為界，成本會再降一次（v3.1 草案）；R11 不必等環境。

**隨手記有一個缺口，必須同批處理【待確認】。** 隨手記填了標題就是 `thinking`（v2 C.2），而那張表單沒有標籤欄，只有在 `?tag=` 篩選生效時才會自動帶入一個。R11 上線後，這條路徑會被規則擋下。兩種做法：

- 隨手記在填了標題時顯示標籤推薦列；或
- 沒有標籤時不直接送出，改走「展開」進入完整表單。

本草案建議前者。U18 已經讓隨手記隨著標題欄即時顯示「將存為 思考」，推薦列跟著同一個判斷出現，不多一次跳頁；後者會讓一次正常的送出看起來像被退件。

## 7. 介面調整

### 7.1 Markdown 檔下載【已定，內容待確認】

卡片頁的複製鈕旁邊加一顆下載鈕，把卡片存成 `.md` 檔。

- **動機**：把內容交給 AI 發想時，直接給檔案比貼上剪貼簿方便。
- **實作**：原文已經印在 `.body[data-md]` 上（v2.2 §4），前端直接由它產生檔案，不新增路由。`icon.eta` 補一個 `download` 圖示。
- **檔名**：`{標題}.md`。碎片沒有標題，或標題含檔名不允許的字元時，退回 `{id}.md`。

檔案內容有三個方案【待確認】：

| 方案 | 內容 | 取捨 |
|---|---|---|
| A | 只有內文，與複製鈕相同 | 最簡單，但檔案裡看不出這是哪一張卡 |
| B | `# 標題` 加內文；碎片只有內文 | 建議的第一版。仍然只需要前端 |
| C | B 加上游脈絡：沿連結往上，把被引用的卡片依序附在後面 | 對 AI 最有用，因為單張短卡的脈絡很薄；需要伺服器組裝，工程量最大 |

### 7.2 標籤頁預設排序改為最近使用【已定】

`/tags` 的預設排序由「數量」改為「最近使用」，方便檢視最近在想什麼。三個分頁全部保留，順序改為：最近、數量、名稱。

- **改動**：`routes.ts` 的預設值與分頁順序；`tags.eta` 判斷「哪一個分頁不帶 `?sort=`」的那一行；斷言「索引頁預設按數量」的測試。
- 表單的標籤推薦原本就按最近使用排序，不受影響。
- 本項修訂 v2.2 §8 的預設值。

### 7.3 碎片編輯頁修正【已完成】

碎片送出後再編輯，整段文字會擠進單行的標題欄，瀏覽器會丟掉其中的換行，一存檔就壓成一行。

修正後，碎片的編輯頁與建立表單一致，只有一個大文字框，換行會保留。已經被壓成一行的舊碎片沒有修復，原文要從 git 歷史取回。

**未採納**：在編輯頁為碎片補上標題、使它升格為 `thinking`。那需要鬆動「型別不可改」（v2 D.3），目前沒有這個需求。

## 8. 暫不處理

以下在討論中出現過，本草案不處理，記錄在此以免日後從頭討論。

- **定案後往內文追加。** 進度控管的母訊息需要在被引用之後繼續補充，而 R6 讓母卡一被指向就定案。§3 讓沒有被引用的卡片可以一直改，但母卡正是會被引用的那一種，所以這一項仍然存在。一個可行的方向是「定案後內文只能往後追加，既有區塊不動」：既有的 `#b{n}` 錨點不會位移，R6 要保護的東西仍然成立。這要改動 R6，需要單獨討論。
- **規劃類內容的整合。** 情報、時程、待辦與考量混在一起的長週期規劃，目前在一個頻道裡還負荷得住，也還沒有整合這些離散訊息的想法。
- **圖片與檔案的保存。** 例如課表圖片、檔案傳輸。
- **作品的章節。** 長篇作品切成章節，需要一條「屬於」的關係。`part-of` 的介面用字是「節錄自」，用在章節上不對。等實際寫到長篇再談。
- **正文引用參與定案。** v2 G 節否決過。§3 之後，只被正文引用的卡片會一直可改（§3.4）；實際出現問題再重新評估。

## 9. 裁決紀錄（G 節補充）

1. **否決為個別流程做專屬功能**（§1.3）。流程是習慣，還會變；機制只提供原件。
2. **勾選是狀態，不是修改**（R14）。
3. **否決「一張卡一件待辦、以連結標記完成」。** 待辦的單位是一則內文裡的條列，不是一張卡一件事。
4. **未被引用的卡片，文字隨時可以修改**（§3）。時間限制對小修正與補述的意義不大，需要保護的東西由 R6 負責。連結與刪除的期限另行確認（§3.2、§3.5）。
5. **產出從思考分出來，成為獨立型別**（§4）。判準沿用 v2 A.1「錯的時候該怎麼修」；名稱待定。
