## 1. 背景：為什麼是這個方向

### 1.1 設計假設與實際用法的落差

v2 的設計假設是「單一主題、長脈絡的深入思考」：資料進來、重述、形成思考，三份待處理清單負責提醒哪些東西還沒被接住。

實際的用法是另一種：**把想法連起來，做短脈絡的延伸**。思緒很快，而且是網狀擴張，反覆編修一份文件的方式並不適合。由此得到三個觀察：

1. **跨分野的雜訊。** 首頁是一條混著所有主題的時間軸，不同脈絡的內容互相干擾。這一項由 v3.1 草案的環境回應。
2. **離開 Discord 只完成一部分。** Skynote 的另一個目的是取代 Discord 作為個人紀錄的地方。目前只有「發想與思辯」搬過來，其餘仍在 Discord（見 §1.2）。
3. **不可變的價值在放鬆，不在限制。** 寫完就不必回頭維護，這是它有意義的地方。它不是一項硬性需求，而是從「通常不會回頭編輯舊內容」推導出來的可行用法。勾選（§2）與產出不設反芻期（§3）都從這一點出發；其餘型別的修改期限移到 v3.1 草案討論。

### 1.2 還留在 Discord 的使用方式

下表記錄的是目前的習慣，不是定型的流程，日後還會變。

| 方式 | 做法 | 以 Skynote 現有機制表達 | 缺口 |
|---|---|---|---|
| TODO | 每天開一則新訊息；當天之內在同一則增刪；完成的按表情標記 | 一張卡加上反芻期 | 一個放的地方；標記完成 |
| 紀錄 | 有情報就往裡面丟 | 隨手記 | 一個放的地方 |
| 想做的事 | 想到就丟；不定期發一則整理目前狀況的訊息 | 隨手記；整理就是一張新卡 | 一個放的地方 |
| 進度控管 | 一則母訊息，加上每天的進度更新 | 母卡，加上連回它的子卡；下游串即時間軸 | 母卡被引用後就定案，無法再補充（§8） |
| 規劃 | 情報、時程、待辦、考量混在一起 | 暫無對應 | 目前沒有搬遷的需求（§8） |
| 旅遊紀錄 | 同一處混用 TODO 與紀錄 | 同上兩列 | 一個放的地方 |

幾乎每一列缺的都是同一樣東西：**一個放的地方**。這由 v3.1 草案的環境回應；本文件處理的是「標記完成」。

### 1.3 設計原則

**機制只提供原件，流程留在使用習慣裡。**

上表的每一種方式，在 Discord 裡都不是功能，而是習慣。Discord 只提供幾個原件：一個地方、發一則、短時間內改一則、按一個表情。流程是在上面長出來的，所以自由，也所以還能繼續變。

v2 走的是相反的路：它把一套流程（資料、重述、思考，加上 rel 矩陣）寫成規則，而那套流程與實際用法對不上。把上表逐項做成功能，會重演同一個問題，而且會得到互不一致的規則。

v3 因此只補兩個原件：**勾選**（§2）與**環境**（v3.1 草案）。本文件其餘各項不是新原件，而是對既有機制的調整：§3 把產出從思考裡分出來，§4 讓隨手記只寫碎片，§7 讓手動調整的結果拉得回來。

## 2. 待辦勾選

### 2.1 語法【已定，寫法待確認】

支援 `[ ]`（未完成）與 `[x]`（完成，`[X]` 同義），渲染成可以點的核取方塊。

標記必須在清單項目的開頭【待確認】：

```markdown
10/7
- [ ] 09:00 交作業
- [x] 買車票
1. [ ] 也可以用編號清單
```

要求清單項目，是為了與 GitHub 及其他 Markdown 工具的寫法一致：下載的 `.md`（§6.1）拿到別處仍然是待辦清單。行首沒有清單記號的 `[ ] 事情` 不視為標記。

### 2.2 規則

**R14（候選）. 切換勾選標記不算修改卡片，任何時候都可以切換。**

勾選不受反芻期（R5）限制【已定】，也不受定案（R6）限制【待確認】。

- **為什麼不算修改**：不可變的意義在於寫完不必回頭維護（§1.1），而不在於禁止狀態改變。勾選記錄的是「這件事做完了」，不是對內容的修訂。
- **為什麼不牴觸 R6**：R6 守護的是段落錨點 `#b{n}`。切換一個字元不改變區塊的數量與順序，所有錨點照舊有效。

為了不讓這條規則變成編輯的後門，邊界如下：

1. 一次請求只改一個標記，而且只在 `[ ]` 與 `[x]` 之間互換。**內容只差那一個字元。** 原本寫的是「檔案內容逐位元相同」，已放寬：那個字元是伺服器自己換的，再比對一次等於檢查自己的輸出；而一般的寫入會重新產生 frontmatter，手改過的檔案重寫之後不會逐位元相同，要守住那一條就得另開一條直接改原始文字的寫入路徑。
2. 新增或刪除待辦項目、修改項目的文字，仍然是編輯，受反芻期限制（產出沒有反芻期，只受 R6 限制，§3.3）。
3. 勾選不更新 `revised`【待確認】，那個欄位記的是內容的修訂。變更仍然留在 git 歷史裡。
4. 勾選不改變反芻狀態，不會讓卡片重新出現在沉澱清單。

v3.1 草案若讓未被引用的卡片一直可改，R14 實際作用的就只剩被引用的卡片，以及不更新 `revised`；寫法不必改。

### 2.3 實作要點

- **渲染**：`markdown-it` 沒有內建這個語法。在 `render.ts` 加一條規則，做法比照既有的 `block_anchor`：把清單項目開頭的標記換成核取方塊，並依出現順序給序號 `data-task="k"`（從 0 起）。
- **定位**：伺服器要找出原文裡的第 k 個標記。定位必須使用渲染器自己的解析結果（token 的來源行號），不得另寫正規表示式——程式碼區塊裡的 `- [ ]` 不是標記，兩套判斷遲早會對不上。
- **分層**：定位在路由完成，因為 service 不能引用 web 的 `render.ts`（v2 F 節的單向依賴）。service 只收到那個位置，換掉那一個字元。
- **端點**：`POST /c/:id/tasks/:k`，內容為 `{ "checked": true, "rev": "…" }`。`rev` 是頁面載入時卡片內容的雜湊；與現況不符就回 409，前端重新載入。這擋的是另一個分頁改過內文、序號已經對不上的情況。
- **編輯表單也帶 `rev`**【已定】：產出沒有反芻期，會長期修改。兩台裝置都開著編輯頁時，舊的那頁一存，就會無聲蓋掉另一頁存下的內容；在卡片頁勾過的項目也一樣。編輯頁載入時一併帶上 `rev`，`PUT /c/:id` 與現況不符就回 409。它只在存檔時提醒，不合併兩邊的內容。`rev` 因此涵蓋整張卡的內容（標題、標籤、網址、內文），不只是內文。
- **碎片**：碎片的文字存在 `title`（v2 A.5 的欄位反轉），勾選改的是 `title`。讀寫一律經過 `fleetingText` 與 `fleetingDraft`。
- **寫入**：沿用既有的寫入路徑，即寫檔、更新索引、一個 commit，commit 訊息為 `check {id}`。
- **介面**：只有卡片頁可以勾。列表摘要與來源對照面板不提供。沒有 JavaScript 時核取方塊顯示為唯讀。
- **複製與下載**：交出去的原文照樣帶著 `[x]`。

### 2.4 與 TODO 習慣的對應

每天一張卡。當天在反芻期內增刪項目，做完的勾掉；過了反芻期，項目不能再改，但仍然可以勾。

`EDIT_WINDOW_HOURS` 維持全域一個值，不為 TODO 另設長度。

## 3. 新型別：產出

### 3.1 定位【已定】

產出是做出來的成品的紀錄：寫成的文章、故事、報告等。它和思考的定位不同：思考記錄的是主張與推論，產出記錄的是成品。名稱用「產出」而不用「創作」，因為「產出」比較泛用。

依 v2 A.1 的判準「這張卡錯的時候該怎麼修」：

| type | UI 標籤 | 對誰負責 | 錯的方式 | 修法 |
|---|---|---|---|---|
| `thinking` | 思考 | 對世界負責 | 命題為假 | 換一個主張，發新的 thinking `updates` |
| `output` | 產出 | 對成品本身負責 | 沒有做成想要的樣子 | 改稿；被引用之後發新版本 `updates` |

思考問的是「這是真的嗎」，產出問的是「這是我要的樣子嗎」。把成品寫成 `thinking`，會讓兩種錯混在同一格；而成品不提出命題，`supports`、`refutes`、`contradicts` 對它也沒有意義。

型別 ID 暫定 `output`，與 UI 名稱對應【待確認】。型別名寫進卡片檔之後就改不掉（v2 D.3），實作前要定案。

### 3.2 為什麼是型別，不是標籤

- 型別決定錯的時候怎麼修，以及能用哪些關係（v2 A.1、A.3）。產出與思考在這兩點上都不同。
- 標籤的職責是主題普查（舊草案 §1）。用標籤標出「這是成品」，會讓同一個欄位同時表達主題與性質。

### 3.3 不設反芻期【已定】

**R15（候選）. `output` 不設反芻期：被引用（R6）之前，修改、新增連結（R7）與刪除（R9）都不受時間限制。**

- **產出需要反覆改稿。** 反芻期一過就只能發新版本的話，每改一次就多一張卡。
- **定案照舊由 R6 決定。** 被引用之後，修改以新版本（`updates`）延續。應用程式產生的段落連結只有一個來源：來源面板的「引用」鈕，而那條路徑一定帶著指回同一張卡、拿不掉的連結（v2 C.3、R7），所以都在 R6 的保護範圍內。不受保護的只剩手動貼進正文的網址；需要穩定的錨點時，建立連結。
- **連結照舊只增不減**（R7）。改稿時用上新的材料，隨時可以補上取材的連結（§3.4）。加錯的連結，在被引用之前都可以整張刪掉重建；代價是新卡換了 ID 與建立時間。
- **修改視同建立的一部分**（R4）：不論何時修改，都要通過當下的現行規則。

連帶的變化【待確認】：

- **沉澱清單不列產出。** 沉澱是「還在反芻期內」的卡片，產出沒有反芻期。
- **卡片頁與編輯頁不顯示反芻倒數。** 編輯頁改為一行說明：「被引用之前都可以修改」。
- **`ruminationOf` 多收型別。** 未被引用的產出，回答「開著，沒有期限」。

### 3.4 關係矩陣【待確認】

從 `output` 出發：

| rel | 目標 | 意圖 |
|---|---|---|
| `updates` | `output` | 新版本取代舊版本 |
| `related` | 任意 | 取材：這份產出從哪些材料與想法長出來 |

指向 `output`：

- `thinking` 的 `related` 目標本來就是任意型別，加入新型別後自動涵蓋。
- `thinking` 的 `about` 目標加上 `output`【待確認】：這則思考在討論這份產出，例如寫完之後的檢討。
- 其餘不開放：成品不提出命題，`supports`、`refutes`、`contradicts` 指向它沒有意義；`restatement` 依 R1 只錨定資料。

介面用字沿用既有的 rel，不新增。

**`related` 開放給 `output`，部分推翻 v2 A.3「`related` 只開放給 `thinking`」。** 那一條的理由是：`related` 是唯一弱語義的關係，每一型都能用的話，會變成逃避定義關係的逃生口。這對產出不成立——產出與取材對象之間本來就沒有更精確的關係可以選，`related` 不是在逃避哪一條。

另一個做法是新增一條專用的關係（例如「取材自」）。詞彙表、圖示（v2.2 §3）與介面用字都要跟著加，本草案不建議。

### 3.5 建立入口【待確認】

- **隨手記的「展開」**【已定】：完整表單上在思考與產出之間二選一，預設思考（§4.3）。產出常常不是從某一張卡衍生出來的，屬於 v2 C.2 所說「無任何參照的初始卡片」，這就是它的全域入口。原本提的側欄「建立產出」已撤回：產出的欄位與思考一樣，在展開之後選就夠了。
- **卡片頁的 `+`**：
  - `thinking` 與 `fleeting` 加一顆「建立產出」【已定】，建立 `output`，以 `related` 指回。想法做成成品，是產出最常見的來處。
  - `output` 自己的選單：「更新」（建立 `output`，`updates`）與「發想」（建立 `thinking`，`about`；若 `about` 不開放給 `output`，改用 `related`）。
  - `original` 與 `restatement` 先不加，選單已經有四顆。

### 3.6 欄位與呈現【待確認】

- **欄位**：標題、內文、標籤、連結，與 `thinking` 相同。`url`、`provenance`、`source_*` 為 `null`。發表處的網址，等到有需要再開。
- **標籤**：不強制（§4.1）。
- **色點**：偏紅的色調【已定】。`#D16E8F`（OKLCH L 0.66 / C 0.13 / h 0°）。第一版 `#BE6877`（L 0.62 / C 0.11 / h 10°）實看跟思考的棕色太近，改成更亮、彩度高一階、往玫瑰紅轉；OKLab 色差對思考 0.127 → 0.147，對 `--alert`（`#B4483F`，只用在錯誤訊息與刪除鈕）0.090 → 0.134。U27「四個型別色是畫面上唯一的彩色」改為五個。
- **列表 meta 行**：比照 `thinking`，即 `產出 · 出向 N · 入向 M`。
- **首頁與搜尋的型別篩選**：多一個選項，由 `CARD_TYPES` 自動產生。

### 3.7 既有卡片

已經寫成 `thinking` 的產出維持原樣。型別不可改（v2 D.3），規則不追溯（R4）。要歸到產出，就發一張新的 `output`，以 `related` 指回；或者手動改檔，再用側欄的「更新」取回（§7）。手動改型別繞過了 D.3，被牽動的連結若因此違反矩陣，重建報告會列出來（R4）。

## 4. `thinking` 需要標籤（沿用舊草案）

### 4.1 規則

**R11（候選）. `thinking` 至少需要一個標籤；其餘型別不強制。**

- **`fleeting` 必須維持免標籤**：碎片的價值在於零決策輸入，必填標籤會摧毀這個體驗。
- **`fleeting` 的缺口會自己補上**：碎片被完整化成 `thinking` 時，標籤自然補上。
- **`original` 與 `restatement` 不強制**：`original` 沒有脈絡可以繼承，強制的成本最高；`restatement` 依 R1 錨定原文，脈絡已經由原文提供。
- **`output` 不強制**：產出常從隨手記展開建立（§3.5），沒有可以繼承的標籤，處境與 `original` 相同。
- **不追溯**（R4）：既有的無標籤 `thinking` 維持原樣，重建索引時列入警告清單。反芻期內的修改視同建立，不能把標籤刪到一個不剩。

### 4.2 與舊草案的差異

舊草案把 R11 與封閉詞彙表（R13）綁在同一批上線，由後者把強制的成本降成「從清單點選」。本文件不採納 R13，所以 R11 單獨成立，成本由卡片頁 `+` 的標籤繼承壓低：從卡片頁衍生的 `thinking` 會自動帶入來源卡的標籤（v2 C.3）。環境上線後，標籤推薦以環境為界，成本會再降一次（v3.1 草案）；R11 不必等環境。

### 4.3 隨手記只寫碎片【已定】

隨手記填了標題就是 `thinking`（v2 C.2），而那張表單沒有標籤欄。R11 上線後，這條路徑會被規則擋下。

做法：**隨手記移除標題欄位，只建立碎片。要記成思考，就按「展開」進入完整表單**，那裡有標籤欄與推薦列。

- **改動最小**：R11 不必在隨手記另外處理。
- **意圖一致**：隨手記是碎片的入口，思考與產出一律走完整表單。
- **「展開」**：隨手記裡的文字帶進完整表單的內文，型別在思考與產出之間二選一，預設思考【已定】。兩型的欄位一樣，驗證失敗退回時這個選擇照樣留著。
- **`?tag=` 篩選的自動帶入保持原樣**（v2.2 §6）：隨手記的標題顯示「隨手記 · #標籤名」，送出時帶上那個標籤；展開時填進標籤欄，可以自由修改。
- **U18 撤回**：隨手記只會存成碎片，沒有要顯示的判斷。送出鈕固定為「記為碎片」。
- 舊草稿（`quick` 槽）裡的標題不再還原。

**未採納**（上一版的兩案）：隨手記在填了標題時顯示標籤推薦列；或沒有標籤時改走「展開」。前者讓浮動小框變重；後者讓一次正常的送出看起來像被退件，而且「填了標題就是思考」那條規則還在。

### 4.4 改動檔案

| 檔案 | 改動 |
|---|---|
| `src/domain/rules.ts` | R11 的檢查，建立與修改共用 |
| `src/domain/card.ts` | `quickDraft` 不再依標題決定型別 |
| `src/web/routes.ts` | `POST /quick` 只建立碎片；展開時把文字帶進內文 |
| `src/web/views/layout.eta`、`public/js/app.js` | 移除標題欄與 U18 的動態文字 |
| `src/store/index/rebuild.ts` | 警告清單加上 R11 |

## 5. 側欄卡片索引替換為標籤清單（沿用舊草案）

側欄下半的「卡片索引」，定位是建立連結時的名稱參照工具（v2 B.3）。把它換成標籤清單，會抽掉手動連結流程的輔助，所以有前置條件。

**前置依賴鏈**：
`v2.2 草稿暫存` → `連結列行內選卡器（快速搜尋引用）` → `側欄卡片索引替換為標籤清單`

前兩項都已經完成：連結列打標題就會搜尋（`/api/search`），2026-09-06 就有了，比舊草案把它列為前置條件還早。所以這一項現在就能做（已定）。

替換之後，標籤清單依最近使用排序，與標籤頁的預設排序一致（§6.2）；它與表單的標籤推薦是同一份，不列鎖定的標籤。環境上線後，以目前環境為範圍（v3.1 草案）。

**修正（已定）：不整個換掉，依頁面切換。** 整個換成標籤之後，讀卡、寫卡時少了一眼看得到的名字——選卡器要先打字才找得到。所以文章一覽（首頁、搜尋、標籤頁、各份清單）列最近的標籤，卡片頁與編輯介面（卡片頁、編輯頁、建立表單）列最近的卡片，正在看或正在改的那一張標起來。

## 7. 側欄「更新」：取回語料庫的最新版本

### 7.1 動機【已定】

版本更改的時候，要有方法抓取手動調整後的結果。例如改版需要手動調整卡片檔：在別處的語料庫 clone 裡改好、push 上去之後，伺服器上的語料庫要能拉回來，索引也要跟著重建。

### 7.2 介面【待確認】

- 側欄加「更新」【已定】。動作與工具的順序：追加外部資料、搜尋、標籤、更新。
- 它是一顆送出 `POST /update` 的按鈕，外觀與側欄其他項目相同。不做成連結，因為 GET 不該有副作用。
- 結果頁說明這次發生了什麼：已是最新、取回了哪些 commit（`git log --oneline 舊HEAD..FETCH_HEAD`；原本寫「舊 HEAD 到新 HEAD」，但那會把本機被 rebase 重寫的 commit 也算成取回的），或失敗的原因；以及重建報告（筆數、讀不出來的檔案、壞連結、規則警告）。

### 7.3 流程【待確認】

1. 排進 `GitBackup` 的佇列，與 commit、push 走同一條 promise chain，等前面的操作做完。
2. 補上還沒 commit 的卡片（`commitPendingCards`）。
3. `git pull --rebase`。有衝突就 `git rebase --abort`，語料庫回到原狀，回報衝突的檔案，不重建索引。
4. 本機有領先遠端的 commit 就 push。
5. 重建索引，與 `POST /_reindex` 相同。

- **不是 git repository、或沒有 remote**：跳過 2–4，只重建索引。直接在伺服器上改檔的情況也用得到。
- **會等 git 做完才回應**，不是 fire-and-forget。pull 加上逾時，逾時視同失敗：它走的是備份共用的那條佇列，卡住會擋住之後所有的 commit 與 push。卡片的寫入路徑不受影響（MVP I5）。
- **用 `--rebase` 而不是 `--ff-only`**：push 失敗時，本機會有還沒推上去的卡片 commit，`--ff-only` 會在這時候拒絕；rebase 只重寫那些還沒推上去的 commit。

### 7.4 手動調整的範圍

手動改檔可以繞過應用程式的規則，例如改型別、改已定案的卡。這是刻意留的出口：改版時的資料調整由使用者自己負責。重建報告會列出因此違反現行規則的卡片（R4）與壞掉的連結。

`tags.yml` 也在語料庫裡（v2.2 §7.2），同一個動作會一起取回。

### 7.5 名稱【待確認】

卡片頁 `+` 選單裡也有一顆「更新」（發新版本，`updates`）。兩者同名不同義，v2.1 U8 曾為同樣的理由改過名。不過兩者不會出現在同一個地方，本草案建議維持「更新」。

### 7.6 改動檔案

| 檔案 | 改動 |
|---|---|
| `src/store/backup.ts` | `pull()`：走同一條佇列、可以等待、回報結果 |
| `src/service/`（新檔） | 更新的流程：取回之後重建 |
| `src/web/routes.ts`、`src/web/views/`（結果頁） | `POST /update` |

## 8. 暫不處理

以下在討論中出現過，本草案不處理，記錄在此以免日後從頭討論。

- **定案後往內文追加。** 進度控管的母訊息需要在被引用之後繼續補充，而 R6 讓母卡一被引用就定案。v3.1 草案的「未被引用的卡片可以一直修改」也幫不上，因為母卡正是會被引用的那一種。一個可行的方向是「定案後內文只能往後追加，既有區塊不動」：既有的 `#b{n}` 錨點不會位移，R6 要保護的東西仍然成立。這要改動 R6，需要單獨討論。
- **規劃類內容的整合。** 情報、時程、待辦與考量混在一起的長週期規劃，目前在一個頻道裡還負荷得住，也還沒有整合這些離散訊息的想法。
- **圖片與檔案的保存。** 例如課表圖片、檔案傳輸。
- **產出的章節。** 長篇的產出切成章節，需要一條「屬於」的關係。`part-of` 的介面用字是「節錄自」，用在章節上不對。等實際寫到長篇再談。
