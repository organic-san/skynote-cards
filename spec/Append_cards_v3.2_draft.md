## 1. 首頁短文的顯示範圍拉長【待確認】

文章不長的時候，在首頁多顯示一些，不必點進去才讀得完。

現況有兩道截斷：伺服器的 `excerpt()` 把內文壓平成 90 字並去掉換行，CSS 再截成兩行（v2.1 的 U34）。只改 CSS 沒有用。

建議的做法：

- 字數上限提高，並保留換行。
- 行數上限由 2 行提高到約 6 行。
- 列表上不渲染 Markdown。
- 只作用於時間軸；搜尋結果維持命中片段。

以上數值皆為暫定。

## 2. 未被引用的卡片可以一直修改【暫緩】

> v3 決定反芻期暫時保留（v3 草案 2 §9），v3.1 沒有處理。本節保留提案與分析，等需要時再決定。

### 2.1 動機

反芻期（R5，預設 8 小時）原本的用意，是留一段時間回頭審視與潤飾（v2 D.1）。實際用下來，這個期限對修正小錯誤與補述的意義不大。

檢查它實際保護了什麼：需要保護的是**被依賴的東西**，而那由 R6 負責——被指向的卡片定案（v2 D.2）。沒有被指向的卡片，改了也不會讓任何結構化連結失效（正文裡的段落連結見 §2.5）。時間限制在 R6 之外多擋下的，是對沒人依賴的卡片所做的修改，小修正與補述就屬於這一類。

v3 的產出已經走在前面：產出不設反芻期，被引用之前修改、加連結、刪除都不受時間限制（v3 §3）。本節要決定其他型別是否跟進，以及跟到哪裡。

### 2.2 做法一：只放開文字欄位（本草案建議）

**R5（修訂候選）. 卡片自建立起有一段反芻期，長度由 `EDIT_WINDOW_HOURS` 決定，預設 8 小時。反芻期只管連結的新增（R7）與刪除（R9）；文字欄位的修改不受反芻期限制，只受 R6 限制。**

v2 D.3 的修改約束改為：

| | 反芻期內、未被引用 | 反芻期後、未被引用 | 被引用（R6） |
|---|---|---|---|
| `title` `body` `tags` `url` `provenance` `source_*` | 可改 | 可改 | 不可改 |
| `links` | 只增不減（R7） | 不可新增 | 不可新增 |
| 刪除整張卡（R9） | 可以 | 不可以 | 不可以 |
| `type` `id` `created` | 不可改 | 不可改 | 不可改 |

連結與刪除留在反芻期內，理由有三：

- **刪除是連結的配套。** R9 存在是因為 R7：連結選錯收不回，只能整張刪掉重建（v2 D.4）。如果連結可以一直加、刪除卻只限反芻期，反芻期後加錯的連結就再也沒有補救的方法。兩者必須同一個期限。
- **反芻期後的關聯是新的思考。** 「發現兩個舊想法有關，本身就是一個新的思考，它應該有自己的節點」（MVP I4）。反芻期後要把舊卡連到更舊的卡，就發一張新卡同時指向兩者。
- **刪除比修改重。** 修改留下同一張卡，刪除讓它從時間軸上消失。手滑通常當下就會發現，反芻期足夠。

R4 的但書「反芻期內的修改視同建立的一部分」改為「修改視同建立的一部分」：不論何時修改，都要通過當下的現行規則。規則收緊之後，修改一張不合新規則的舊卡，要在同一次修改裡讓它合規（例如沒有標籤的舊 `thinking`，v3 §4）。

### 2.3 做法二：全部不設期限，比照產出

連結的新增與刪除也取消期限，「能不能動」只剩「有沒有被引用」一個判準。

- **好處**：規則只有一條，反芻期整個退場，所有型別與產出一致。
- **代價**：反芻期後加錯的連結只能整張刪掉重建，而重建會換掉 ID 與建立時間，對一張舊卡來說就是失去它在時間軸上的位置。
- **產出接受這個代價的理由**，是改稿時補上取材的連結是常態（v3 §3）。其他型別沒有這個需要。

### 2.4 連帶的變化

- **判準拆成兩個**（做法一）：「文字能不能改」只看 R6；「連結與刪除能不能動」看 R5 與 R6。
- **卡片頁**：meta 行末尾的「尚可編輯 N 小時」（v2 D.5）移除。文字能不能改不再有期限，留著這個倒數，會讓人以為時間到了就不能改。「編輯」鈕照舊只在可改時出現，判準改為「沒有被引用」。
- **編輯頁**：做法一的倒數改說連結與刪除的期限，例如「連結與刪除還剩 3 小時」；反芻期後，新增連結的區塊與刪除鈕不再出現，換成一行說明。做法二沒有倒數，比照產出。
- **鎖定時的訊息**：只剩被引用一種原因。
- **R14**：未被引用的卡片本來就能改，R14 實際作用的只剩被引用的卡片，以及不更新 `revised`（v3 §2）。
- **`revised`**：每次修改照舊更新。卡片頁的「改於」會比以前常出現，這是預期的。
- **沉澱清單**：已在 v3.1 移除（v3.1 §3），不受影響。

### 2.5 風險：手動貼上的段落連結

R6 只看 frontmatter 的 `links`（v2 G 節「否決正文引用參與定案鎖定」維持，見 v3 草案 2 §9）。應用程式產生的段落連結只有一個來源：來源面板的「引用」鈕，而那條路徑一定帶著指回同一張卡、拿不掉的連結（v2 C.3、R7），所以都在 R6 的保護範圍內。

不受保護的只剩手動貼進正文的網址。期限放開之後，它們指向的段落可能位移；需要穩定的錨點時，建立連結。

## 3. 環境的刪除與卡片的移動【暫緩】

v3.1 提供了環境的建立與改名（v3.1 §2.7）。刪除與移動還沒有介面；需要時的做法如下。

### 3.1 卡片在環境之間的移動

**現況**：在別處的 clone `git mv` 到另一個資料夾、push，再按側欄的「更新」（v3.1 §2.3）。整批搬移（例如把（無環境）搬空）用這條路最省事，也是 v3.1 預期的用法。

**若要在網頁上做**：移動在資料面只是搬動檔案，內容逐位元不變。ID、連結、`/c/{id}`、段落錨點都不受影響，所以不牴觸不可變，也不需要動規則。做法比照環境改名，只是單位是一張卡：

- bucket 先用新名字存一份，成功才刪舊名字；標記的決定方式與改名相同（v3.1 §2.7）。
- 本機搬檔、索引的 `env` 換掉，一個 commit（例如 `mv {id} {舊環境} → {新環境}`）。
- 入口：卡片頁 meta 行旁的一個動作，選目標環境。

**要決定的事**：

- v3.1 §2.6 說「建立之後不能改環境」，那條是為了不讓環境變成一個需要維護的屬性。開放移動就推翻它；放錯了的卡目前只能在反芻期內刪除重建（產出在被引用之前），被引用之後就留在原處。
- 移動要不要受反芻期或定案限制。內容不變，R6 要保護的段落錨點不受影響，所以沒有理由限制；但「定案的卡還在動」可能違反「寫完不必回頭維護」的直覺。

### 3.2 環境的刪除

- **只刪空的環境**：資料夾裡沒有任何卡才可以刪，效果是刪掉那個空資料夾。有卡的環境要先把卡搬走（§3.1）或刪掉（R9，只限反芻期內）。這樣刪除永遠不會帶走卡片。
- 空的環境不在 git 與 bucket 裡（v3.1 §2.7），App Engine 換機器時本來就會消失；需要刪除的情境主要是建錯名字又不想改名、或本機與 VM 上留著的空資料夾。
- 入口：環境面板裡（v3.1 §2.8），只在空的環境那一列出現，例如改名表單旁的一顆「刪除這個環境」。排過序的話，`envs.yml` 裡的名字一起拿掉。
