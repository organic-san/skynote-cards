# append-cards

只有作者一個人能寫、能讀的卡片資料庫。承載三類內容——別人寫的一手材料、
我對這些材料的重述、以及我自己的思考——並讓三者之間的關聯可以被建立與查詢。

資料只新增，不修改。索引、分類、視圖全都是可以隨時刪掉重算的投影，
唯一的真相是檔案系統上那疊 markdown。

---

## 這個系統靠哪幾條規則成立

規則後面的理由比規則本身重要，因為理由決定了哪些「改良」其實是破壞。

**檔案是唯一真相，SQLite 只是索引。**
任何時候刪掉整個 `index.db`，系統都能從 markdown 檔完整重建，結果完全等價。
一疊 markdown 二十年後仍然讀得開，一個 `.db` 不行。

**卡片建立五分鐘後永久不可變。**
沒有 DELETE 端點，沒有超過時窗的修改，沒有任何腳本可以改寫既有卡片。
連結會腐爛是因為它指向可變的目標；目標不可變，連結就永遠有效。

**連結只能指向已存在、而且 ID 更小的卡片。**
這條規則讓「新增連結」永遠只需要寫一個新檔案，不必回頭改舊檔案。
它同時保證整張圖是 DAG，任何節點都能往回追出完整的依賴鏈。

**連結宣告在來源卡片的 frontmatter 裡，沒有獨立的連結物件。**
要連接兩張既有卡片，唯一的方式是建立一張新卡片同時指向兩者——
「發現兩個舊想法有關」本身就是一個新的思考，它應該有自己的節點。

**寫入不會因為備份失敗而卡住。**
git push 失敗、網路斷掉、遠端不見了，卡片一律先寫進本機檔案並回應成功。
寫入摩擦是這個系統唯一的生死線：使用者不會因為一次失敗就放棄，
但會因為每一次延遲而「等等再記」，然後系統安靜地空掉。

**索引重建是冪等的，隨時可以執行。**
`POST /_reindex` 砍掉重建，不需要停機，不需要備份索引。

## 資料長什麼樣子

兩個獨立的 git repository：這個 repo 放程式碼，另一個 repo 放語料庫。
語料庫裡除了 markdown 什麼都沒有，不含任何可執行檔。

```
語料庫/
  cards/
    88822241409303552.md
    88822241571221504.md
  .gitignore          # 忽略 index.db
```

一張卡片一個檔案，檔名就是 ID：

```markdown
---
id: "88822241710055424"
type: thinking
created: "2026-09-03T02:27:52.661Z"
title: 恆星不是近可分解性的反例，但它暴露了賽門沒寫的前提
tags: [物理, 複雜系統, simon]
url: null
provenance: null
revised: null
links:
  - rel: refutes
    to: "88822241409303552"
---

內文，markdown。可以是任意長度。
```

**ID** 是 64-bit 整數的十進位字串：

```
id = ((now - 2026-01-01T00:00:00Z) << 22) | (random 12 bits << 10) | seq(10 bits)
```

同一毫秒內 seq 從 0 遞增，所以先建立的卡片一定有較小的 ID。
ID 裡不編碼類型、主題或層級，也不重用、不重編號。

**三種 type**，建立時必須選一個：

| type | 語義 |
|---|---|
| `original` | 不是我寫的。它不會錯，只會被我抄錯或存錯。裁判是原文。 |
| `restatement` | 我寫的，但對原文負責。它錯的方式是誤讀。裁判是重讀一次。 |
| `thinking` | 我寫的，對世界負責。它錯的方式是命題為假。裁判是世界。 |

**六種 rel**，封閉集合，不接受其他值：

| rel | 語義 |
|---|---|
| `about` | 這張卡在講那張卡 |
| `related` | 有關但關係未定型 |
| `supports` | 那張卡是這張卡的依據 |
| `contradicts` | 兩者不相容，但尚未裁決 |
| `refutes` | 這張卡推翻那張卡 |
| `updates` | 這張卡取代那張卡 |

`provenance` 只有 `original` 可以填（`default` / `translated` / `AI-summarized`，
未指定時是 `default`，而且 `default` 不會顯示在畫面上——這個欄位存在的理由是
標示「這段文字經過了轉換」，沒轉換的時候本來就沒有東西要說）。
`revised` 只有在五分鐘時窗內被改過才有值。

早期的卡片檔裡還有 `archive_url` 欄位，以及 `self` / `published-translation` /
`machine` 三個舊的 provenance 值。卡片不可變，那些字串會永遠留在語料庫裡，
所以解析永遠認得它們；新卡片不再寫 `archive_url`，建立時的 provenance
也只接受上面那三個新值。

## 建立一張卡片時會發生什麼

1. 驗證。任何一項不過就整筆退回 400，不寫任何東西。
   - type 是 original / restatement / thinking 之一
   - title trim 後非空
   - 每個 tag trim 後非空，重複的去掉，不做其他正規化
   - 每條連結的 rel 在詞彙表內
   - 每條連結的目標檔案存在
   - 同 rel 同目標的連結不重複
   - provenance 只在 original 上有意義；別的類型送了也只是被丟掉，不算錯
2. 產生 ID，並確認每條連結的目標 ID 都比它小。
3. 寫檔：先寫 `.tmp`、fsync、再 rename。任何時刻中斷都不會留下半個檔案。
4. 寫索引。失敗只記 log，仍然回應成功——檔案已經在了，索引隨時能重建。
5. 回應 302 導到 `/c/{id}`。
6. 非同步觸發 git commit 與 push，不等它完成。

**警告 W1**：卡片有 `refutes` 或 `updates`，但除了這條連結本身之外，
沒有任何指向 `original` 或 `restatement` 的連結時，卡片頁面上會顯示警告。
不附證據的推翻，跟改變心情無法區分。W1 不擋寫入。

**編輯**：建立後五分鐘內可以改 title、body、tags、url，
改完會設定 `revised`。type、links、id、created 不接受任何形式的修改。
超過五分鐘 `PUT /c/{id}` 回 403，要更正只能建立新卡片並用 `updates` 指回去。

## 端點

| 端點 | 做什麼 |
|---|---|
| `GET /` | 時間逆序的卡片流，支援 `?type=` 與 `?tag=`，一頁 50 筆 |
| `GET /new` | 建立表單，`?type=` 與 `?to=` 決定從哪一段開始、預先連上誰 |
| `POST /new` | 建立卡片 |
| `GET /c/{id}` | 卡片檢視，含出向連結與反向連結 |
| `GET /c/{id}/edit` | 五分鐘時窗內的編輯表單，逾時回 403 |
| `PUT /c/{id}` | 五分鐘時窗內的修改 |
| `GET /tags` | 所有標籤與使用次數 |
| `GET /orphans` | 沒有任何連結的 thinking 卡 |
| `GET /search?q=` | FTS5 全文檢索，中日文逐字建索引所以詞在句中也找得到 |
| `GET /api/search?q=&limit=` | 連結選擇器用，回 JSON |
| `POST /_reindex` | 砍掉重建索引，回報處理筆數、解析失敗的檔案、壞連結清單 |
| `GET /_health` | 卡片檔案數、索引筆數、未 push 的 commit 數 |

沒有刪除卡片的途徑，任何形式都沒有。

三個頁面各自有存在的理由：

- **反向連結**——所有連結都指向過去，沒有反查的話一張卡片對
  「誰用了我、誰推翻了我」完全無知，整個系統會是寫入單向的。
- **`/tags`**——標籤不做正規化也不自動合併。同一件事被寫成
  `偶像大師` / `im@s` / `ML` 三種拼法時，這一頁是唯一看得出來的地方；
  看得到就會自己收斂。
- **`/orphans`**——目前所有沒有依據的信念。這份清單是這個系統最直接的產出之一。

`POST /_reindex` 回報裡的壞連結清單同樣重要：它是這個系統唯一會發現
資料完整性問題的地方。兩種壞法都會被列出——目標不存在，
以及目標 ID 不小於來源 ID。

## 介面

導覽在左側，窄螢幕從左邊拉出來、寬螢幕直接常駐：上面三個去處，
一條線之下是搜尋，中間是最近的卡片（會捲），最下面是建立卡片。
右下角另有一顆常駐的新增鈕，點開是類型選單。

建立表單是一頁到底：類型（三個併排）、title、context、
收合的 url 與 provenance、link、tags、submit。

**從一張卡片開新卡時（`/new?to={id}`）畫面會分成兩個各自捲動的面板**，
左邊是那張卡的完整內文、右邊是表單；寬螢幕左右分、窄螢幕上下分，
中間的分隔線可以拖，比例記在瀏覽器裡。手機上鍵盤一升起來就會吃掉
快一半的視窗，所以比例必須是可調的。

從一張卡片按新增鈕時，新卡會預先連上那張卡，而且只給 `restatement` 與 `thinking`：
從一張卡開出來的新卡是對它的回應，一手材料不會是誰的回應。
這是介面的引導，不是驗證規則——`original` 帶連結仍然合法。

**方向由位置表示，不用文字說。** 上游（這張卡指向誰）放在內文之上，
下游（誰指向這張卡）放在內文之下，各自只有一個箭頭加一個數量。
每一列自己的 rel 字已經說完了「這是哪一種關係」，位置說完了「哪個方向」，
所以標題沒有東西要說，就不放。上游預設只展開一層——要的是「馬上知道
我在回應誰」；下游展開兩層，那是主動探索。

一則兩行：關係加標題，底下是類型與日期。每個節點左邊一條線，
線的顏色就是那條連結的關係。往任一方向走 ID 都嚴格單調，所以不可能繞回來；
同一張卡從不同分支被走到時，只有第一次完整展開，之後標成「上方已展開」。

## 引用原文

在左邊的來源面板選一段文字，按「引用選取的段落」，右邊的內文會多出：

```markdown
> 複雜系統多半是階層式的，子系統內部的互動遠強於子系統之間的互動。
> — [賽門：近可分解系統](/c/88822241409303552#b3)
```

`#b3` 是來源內文的第 3 個頂層區塊。渲染時每個頂層區塊都掛著 `id="b0"`、
`id="b1"`……所以那是原生的 HTML 錨點：瀏覽器自己捲過去，CSS 的 `:target`
把那一段標起來，全程不需要 JS。

**因為卡片不可變，第 3 個區塊永遠是第 3 個區塊**，這個錨點不會腐爛。
這是不可變規則真正換到的東西之一——一般系統裡按位置錨定都是不可靠的。

已知的限制：只標到段落，不標到那一句；選取跨了兩段就錨到第一段。

那個連結是正文裡的 markdown，**不會**進 frontmatter 的 `links`，
所以不會出現在上下游裡。frontmatter 的 links 是宣告出來的、有類型的關係，
正文裡的引用是內容。從卡片按 ＋ 進來時指向那張卡的連結列本來就已經填好了，
兩者在這個流程裡剛好重合。

卡片上的 `url` 認得出格式的就直接嵌在頁面上：YouTube 走
`youtube-nocookie.com` 的 iframe、圖片走 `img`、`.pdf` 走 iframe，
其餘一律只留連結。白名單之外不嵌，因為那些站（X、Instagram 之類）
的官方嵌入都要載入它們自己的 JS，這一頁不放任何第三方腳本。

畫面上飽和的顏色只用在六種關係上，其他一律灰階：內容是實色，
時間、數量、類型這些描述性的東西退到灰色小字。

## 跑起來

需要 Node 22 以上（開發與部署都在 Node 24 LTS 上驗過）。

```bash
npm install

# 語料庫。這是一個獨立的 git repo，跟程式碼分開。
mkdir -p ../corpus/cards && git -C ../corpus init -b main

CORPUS_PATH=../corpus INDEX_PATH=../index.db npm run dev
# http://127.0.0.1:3000
```

| 指令 | 做什麼 |
|---|---|
| `npm run dev` | 開發模式，改檔案自動重啟 |
| `npm run build` | 編譯到 `dist/`，並把模板複製過去 |
| `npm start` | 跑編譯後的版本 |
| `npm test` | 全部測試 |
| `npm run typecheck` | 只做型別檢查 |

環境變數見 `.env.example`：`CORPUS_PATH`、`INDEX_PATH`、`PORT`、
`GIT_AUTHOR_NAME`、`GIT_AUTHOR_EMAIL`。

啟動時如果索引不存在，或索引筆數跟 `cards/` 的檔案數對不上，會自動整個重建。
同時會把只有檔案、沒有 commit 的卡片補上 commit 再推一次——
行程被中斷時佇列裡沒輪到的卡片，靠這一步才不會漏掉備份。

## 測試

`test/acceptance.test.ts` 的十二則對應這個系統的驗收條件，一則一條，編號一致：
建立三種卡片、反向連結顯示、壞連結被擋下、重建索引列出壞連結、
刪掉索引後重啟內容逐字相同、時窗內可改、時窗外 403、沒有刪除途徑、
git 斷線仍然寫得進去、W1 警告、200 張卡片後首頁與搜尋仍在 300ms 內。

`test/rules.test.ts` 蓋的是撐住這些規則的零件：ID 的排序與唯一性、
卡片檔序列化後再解析完全相同、每一條驗證規則、W1 的判定、
頁面渲染、HTML 跳脫、分頁、以及啟動時的補提交。

```bash
npm test
```

## 部署

```
GCP e2-micro (asia-east1)
├── /srv/app          ← 程式碼
├── /srv/corpus       ← 語料庫（git clone，deploy key 具寫入權）
├── /srv/index.db     ← SQLite，不進版控
└── systemd: append-cards.service
```

完整的部署步驟在 [deploy/README.md](deploy/README.md)，
`deploy/` 下另有三份範本：`append-cards.service`、`cloudflared.service`、
`cloudflared-config.yml`。

- 應用程式只監聽 `127.0.0.1:3000`。
- `cloudflared` 以 systemd service 執行，把它接到子網域。
- **不安裝 nginx，不開放任何對外埠**，GCP 防火牆維持全關。
- 驗證掛在 Cloudflare Access（Google IdP）上，只放行作者一個帳號。
  應用程式本身不實作任何登入邏輯，它信任沒被擋掉的流量就是作者。
- `.github/workflows/deploy.yml`：push 到 main → 跑測試 → ssh 進 VM
  `git pull && npm ci && npm run build && systemctl restart`。

語料庫 repo 第一次要自己 `git push -u origin main` 或讓服務自己推第一次；
之後 `/_health` 才數得出未 push 的 commit 數。

## 目前刻意沒有的東西

沒有 LLM 或 AI 介面、沒有 Discord bot 或第二條寫入路徑、沒有圖形視覺化、
沒有附件上傳（只支援外部 URL）、沒有封存連結、沒有標籤自動合併、
沒有多使用者與分享、沒有刪除與封存、沒有草稿自動儲存與範本。

前端沒有框架、沒有打包工具、沒有 CSS 框架：手寫 HTML 加一個 `style.css`，
加上三支各數十行的 vanilla JS（選單與倒數、建立表單、編輯頁送出）。
外部內容只用 `iframe` 與 `img` 嵌，沒有任何第三方腳本。
目標是在手機瀏覽器上能用。
